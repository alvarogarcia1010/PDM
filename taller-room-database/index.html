RankeUCA crece: de una votación a muchas

Hoy el admin deja de manejar una sola votación. Le damos varias preguntas, cada una con sus propias opciones. Es nuestra primera relación en Room.

En la guía pasada guardaste las opciones de una sola votación con Room. Hoy damos el salto natural: que el admin pueda crear varias preguntas, y que cada una tenga sus propias opciones.

Para eso vamos a conectar dos tablas con una relación uno-a-muchos. Ese es el tema central del taller.

La meta de hoy

Evolucionar el admin a múltiples preguntas: una pregunta tiene muchas opciones. Primero el listado de preguntas, y al entrar a una, sus opciones (lo que ya construiste en CP1). Todo local, sin red todavía.

1 · Qué cambia: de una tabla a dos

Hasta ahora tenías una sola tabla: options. Todas las opciones colgaban de una votación implícita. Hoy aparece una segunda tabla, questions, y la conectamos con la de opciones: una pregunta tiene muchas opciones, y cada opción pertenece a una sola pregunta. Eso es una relación uno-a-muchos.

Relación uno a muchos (1 : N): una Question, muchas Option.

La buena noticia: casi todo lo de CP1 se queda igual. Solo agregamos una tabla, la conexión entre las dos, y subimos la versión de la base.

Paso 2La opción ahora pertenece a una pregunta

Acá viene el primer cambio importante. La OptionEntity que ya tenías gana un campo nuevo, questionId, que dice de qué pregunta es esa opción. Y a Room le avisamos que ese campo es una llave foránea:

data/database/entities/OptionEntity.ktMODIFICADO
@Entity(tableName = "options")@Entity(    tableName = "options",    foreignKeys = [        ForeignKey(            entity = QuestionEntity::class,            parentColumns = ["id"],            childColumns = ["questionId"],            onDelete = ForeignKey.CASCADE        )    ],    indices = [Index("questionId")]) data class OptionEntity(     @PrimaryKey(autoGenerate = true)     val id: Int = 0,     val name: String,     val imageUrl: String,    val questionId: Int, )  fun OptionEntity.toModel(): Option {     return Option(         id = id,         name = name,         imageUrl = imageUrl,        questionId = questionId,     ) }

Tres cosas para entender acá:

foreignKeys le dice a Room que questionId apunta al id de una pregunta. Así una opción siempre está amarrada a una pregunta que existe.

onDelete = ForeignKey.CASCADE es muy práctico: si borrás una pregunta, Room borra automáticamente todas sus opciones. No te quedan opciones huérfanas.

indices = [Index("questionId")] es un índice sobre la llave foránea. Room te lo pide (te marca una advertencia si no lo ponés) porque hace rápida la búsqueda de las opciones de una pregunta.

¿Por qué CASCADE?

Porque una opción no tiene sentido sin su pregunta. Si borrás la votación, sus opciones deberían irse con ella. CASCADE hace esa limpieza por vos, automáticamente.

Y actualizá el modelo y el mapper de Option para que lleven el questionId:

data/model/Option.ktMODIFICADO

Paso 3La relación: traer una pregunta con sus opciones

Ya tenemos las dos tablas conectadas. Pero falta una forma de traer una pregunta junto con todas sus opciones de una vez. Para eso Room nos da @Relation. Creamos una clase que no es una tabla: solo junta una pregunta con su lista de opciones.

data/database/entities/QuestionWithOptions.ktNUEVO
data class QuestionWithOptions(
    @Embedded val question: QuestionEntity,
    @Relation(
        parentColumn = "id",
        entityColumn = "questionId"
    )
    val options: List<OptionEntity>
)

fun QuestionWithOptions.toModel(): Question {
    return Question(
        id = question.id,
        title = question.title,
        optionCount = options.size,
    )
}

@Embedded mete los campos de la pregunta dentro de este paquete. @Relation le dice a Room cómo encontrar sus opciones: "buscá en options todas las que tengan questionId igual al id de la pregunta". Room arma esa lista por vos.

La idea clave

Vos definís la relación una vez, y Room junta los datos de las dos tablas. En la lista de preguntas vamos a usar este paquete para mostrar el título y, de paso, cuántas opciones tiene cada una (options.size).

Paso 4Los DAO

El DAO de preguntas trae la lista con sus opciones, usando la clase de relación del paso anterior. Fijate en el @Transaction:

data/database/dao/QuestionDao.ktNUEVO
@Dao
interface QuestionDao {

    @Transaction
    @Query("SELECT * FROM questions")
    fun getQuestionsWithOptions(): Flow<List<QuestionWithOptions>>

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertQuestion(question: QuestionEntity)

    @Delete
    suspend fun deleteQuestion(question: QuestionEntity)
}
¿Para qué el @Transaction?

Para traer una pregunta con sus opciones, Room hace por detrás dos consultas (una a questions y otra a options). @Transaction garantiza que esas dos lecturas pasen juntas y consistentes. En relaciones, va siempre.

Y al DAO de opciones le cambiamos la consulta: ahora trae las opciones de una pregunta. El insert y el delete quedan igual:

data/database/dao/OptionDao.ktMODIFICADO
 @Dao interface OptionDao {     @Query("SELECT * FROM options")    fun getAllOptions(): Flow<List<OptionEntity>>    @Query("SELECT * FROM options WHERE questionId = :questionId")    fun getOptionsForQuestion(questionId: Int): Flow<List<OptionEntity>>      @Insert(onConflict = OnConflictStrategy.REPLACE)     suspend fun insertOption(option: OptionEntity)      @Delete     suspend fun deleteOption(option: OptionEntity) }

Paso 5Subir la versión de la base

Cambiamos el esquema (una tabla y una columna nuevas), así que Room necesita saberlo. En la AppDatabase agregamos la nueva entity y su DAO, y subimos la versión de 1 a 2:

data/database/AppDatabase.ktMODIFICADO
 @Database(    entities = [OptionEntity::class],    version = 1,    entities = [QuestionEntity::class, OptionEntity::class],    version = 2,     exportSchema = false ) abstract class AppDatabase : RoomDatabase() {     abstract fun questionDao(): QuestionDao     abstract fun optionDao(): OptionDao      companion object {         @Volatile         private var INSTANCE: AppDatabase? = null          fun getDatabase(context: Context): AppDatabase {             return INSTANCE ?: synchronized(this) {                 Room.databaseBuilder(                     context = context.applicationContext,                     klass = AppDatabase::class.java,                     name = "rankeuca_database"                 )                     .fallbackToDestructiveMigration(false)                     .build()                     .also { INSTANCE = it }             }         }     } }
Importante: por qué se borran los datos

Como cambiaste el esquema y subiste la versión, Room ve que la base vieja (versión 1) ya no coincide. Con fallbackToDestructiveMigration, en vez de migrar, borra la base y la crea de nuevo. Es decir, las opciones de prueba de CP1 se pierden. En clase no importa; en una app real escribirías una migración. Y si te olvidás de subir la versión, la app falla al abrir. Ese es el error clásico de "cambié el esquema y no subí la versión".

Paso 8ViewModels y pantallas

Acá no hay nada nuevo de fondo: son los mismos patrones que ya armaste en CP1. Por eso esta parte la hacés vos. Te dejo las dos piezas nuevas como reto, y abajo sí te muestro los cambios que hay que hacerle a los archivos de opciones (que son más sutiles).

Las dos piezas que armás vos

Tu turno · QuestionsViewModel

Armá el QuestionsViewModel. Es prácticamente un calco de tu OptionsViewModel de CP1, pero con Question y sin el questionId. Debe:

  • Recibir el QuestionRepository por constructor.
  • Exponer questions como StateFlow<List<Question>> usando stateIn (igual que options en CP1).
  • Tener addQuestion(title) y deleteQuestion(question), cada una con un viewModelScope.launch que llama al repo.
  • Un companion object con el Factory que saca el repo del AppProvider con provideQuestionRepository().

Pista: abrí tu OptionsViewModel, copiá la estructura y reemplazá opción por pregunta.

Tu turno · QuestionsScreen

Ahora la QuestionsScreen: la lista de preguntas. Es tu OptionsScreen de CP1 con un par de diferencias. Debe:

  • Tener un Scaffold con TopAppBar (título "Preguntas") y una acción "Nueva" que abra un bottom sheet con un solo campo: el título de la pregunta.
  • Mostrar un estado vacío cuando todavía no hay preguntas.
  • Listar las preguntas en tarjetas (LazyColumn + ElevatedCard). Cada tarjeta muestra el título, el texto "${optionCount} opciones" y un botón para borrar.
  • Recibir un onQuestionClick: (Int) -> Unit y llamarlo con question.id al tocar la tarjeta (para navegar a sus opciones).
  • Crear el VM con QuestionsViewModel.Factory y observar con collectAsStateWithLifecycle.

Pista: la tarjeta de opción ya casi lo hace. Acá el bottom sheet pide solo el título, y la tarjeta es clickeable.

Los cambios en los archivos de opciones

Estos dos sí te los muestro como diff, porque el cambio (pasar el questionId y el Factory que lo recibe) es más fino.

La navegación, en una línea

Tenés dos destinos: la lista de preguntas y las opciones de una pregunta. Cuando tocás una pregunta, navegás al segundo destino pasándole el questionId. Eso es lo único nuevo de navegación; el resto ya lo manejás.

Checkpoint final

Para darlo por bueno

Creá dos preguntas. Entrá a una y agregale unas opciones; volvé a la lista y fijate que el conteo de opciones es correcto. Cerrá y reabrí la app: todo sigue ahí. Por último, borrá una pregunta: sus opciones se van con ella (eso es el CASCADE funcionando).

Si algo no funciona, revisá lo más común: ¿subiste la versión a 2?, ¿agregaste la QuestionEntity y el questionDao() en la AppDatabase?, ¿el @Index en la llave foránea?

Lo que NO cambió

Mirá todo lo que no tocaste: el patrón MVVM + Repository, el AppProvider, Room como fuente de la verdad, los ViewModel con stateIn, las pantallas observando con collectAsStateWithLifecycle. Toda esa base se quedó igual. Solo agregaste una tabla y una relación, y la estructura lo absorbió sin romperse. Esa es la señal de una buena arquitectura, y es justo la lección del taller.

Ejercicio extra: para los días de asueto

Estos días no nos vemos por el asueto, así que acá va práctica para reforzar lo aprendido. Son tres pasos sobre la misma RankeUCA, y esta vez sin código de guía: el spec lo tenés acá, la solución la sacás vos.

Paso 1 · Refactor de Option

Por ahora la opción tiene name e imageUrl, pensados para "lugares". Pero RankeUCA vota cualquier cosa, así que ese nombre ya no encaja. Refactorizá:

  • Renombrá name a value (el valor que se vota).
  • Hacé la imagen opcional: val imageUrl: String? = null, así una opción puede o no tener imagen.
  • Propagá el cambio por todos lados: OptionEntity, el modelo Option, los mappers (toModel / toEntity) y el campo del bottom sheet donde se crea la opción.
  • Cambiaste el esquema, así que subí la versión de la base de 2 a 3.

Pista: apoyate en el compilador. Apenas renombrés en la entity, te irá marcando cada lugar que falta arreglar. Seguí los errores hasta que compile.

Paso 2 · Editar (la "U" que falta)

Hoy podés crear, ver y borrar, pero no editar. Sumale el editar, tanto a preguntas como a opciones:

  • En cada DAO, agregá un @Update suspend fun que reciba la entity.
  • En el repository, exponé un updateQuestion y un updateOption.
  • En la pantalla, al tocar una pregunta u opción (o un ícono de lápiz), abrí el mismo bottom sheet que usás para crear, pero pre-rellenado con sus datos.

Pista: reusá el bottom sheet que ya tenés, pasándole un Option? opcional. Si llega null, es modo "crear"; si llega con datos, es modo "editar". Un solo componente para las dos cosas.

Paso 3 · Home tipo menú

Que la app abra en un menú, no directo en la lista de preguntas. Una pantalla con tarjetas:

  • Gestor de preguntas → lleva a lo que ya armaste (la lista de preguntas y sus opciones).
  • Votar → una tarjeta deshabilitada con la etiqueta "próximamente". Todavía no la armamos: la votación llega cuando aprendamos a sincronizar lo remoto con lo local.

Pista: el menú es un nuevo destino de navegación, el primero de todos. Cada tarjeta es un Card clickeable; la de Votar va con enabled = false y un texto apagado.

Con eso la RankeUCA queda más completa: un menú de entrada, un gestor completo (crear, editar, borrar) y el lugar listo para cuando integremos la votación.
