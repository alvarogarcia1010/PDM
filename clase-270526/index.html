Enviar datos al servidor con Ktor

"Una app real no solo muestra cosas — también crea, modifica, envía"

Docente: Alvaro García

Recordatorio

¿Dónde quedamos?

Hasta ahora nuestra app ha estado recibiendo datos: la lista de películas, el detalle de cada una. Todo viene de TMDB hacia la app.

Pero las apps reales no son solo de lectura. El usuario también envía cosas al servidor: comentarios, posts, fotos, valoraciones, votos.

💡 Hoy aprendemos el otro lado: cómo enviar datos al servidor con POST. Es el patrón fundamental de cualquier app interactiva.
El cambio conceptual

GET vs POST

HTTP tiene varios métodos. Hasta hoy usamos solo uno — GET. Hoy aprendemos el segundo más importante.

GET Recibir datos del servidor. La URL contiene todo lo necesario. No envía cuerpo.
POST Enviar datos al servidor para crear algo nuevo. Lleva un body con la información.
PUT Actualizar algo que ya existe. (Lo verán más adelante)
DELETE Borrar algo. (Lo verán más adelante)
💡 La diferencia clave: GET no manda datos en el cuerpo de la petición, POST sí. Por eso al hacer POST tenemos que armar y enviar un body.
La API de hoy

JSONPlaceholder — una API para aprender

Vamos a usar JSONPlaceholder, una API pública pensada justamente para practicar. Tiene endpoints para posts, comentarios, usuarios, etc.

El endpoint que vamos a usar:

POST https://jsonplaceholder.typicode.com/posts

Y el body que vamos a enviar:

{
  "title": "Mi título",
  "body": "Mi contenido",
  "userId": 1
}
💡 Importante: JSONPlaceholder es una API fake. El POST devuelve éxito como si hubiera guardado, pero los datos no se persisten. Sirve perfectamente para aprender el patrón.
DTOs

El DTO de request — lo que se envía

Hasta ahora teníamos DTOs de respuesta (lo que llegaba de la API). Para POST, necesitamos un DTO de request: el "molde" del JSON que vamos a enviar.

@Serializable
data class CreatePostRequestDto(
    val title: String,
    val body: String,
    val userId: Int
)

Y el DTO de respuesta — lo que JSONPlaceholder nos devuelve después de crear el post:

@Serializable
data class PostDto(
    val id: Int,
    val title: String,
    val body: String,
    val userId: Int
)
💡 Dos DTOs: uno para lo que enviamos y otro para lo que recibimos. En este caso son parecidos, pero la diferencia importante es que el request no tiene id — el servidor lo genera al crear el post.
Repository

El Repository con .post()

Una nueva función en el Repository hace el POST. El patrón es muy parecido al GET, pero con dos diferencias clave.

override suspend fun createPost(
    title: String,
    body: String
): Result<PostDto> {
    try {
        val request = CreatePostRequestDto(
            title = title,
            body = body,
            userId = 1
        )

        val response: PostDto = KtorClient.client
            .post("https://jsonplaceholder.typicode.com/posts") {
                contentType(ContentType.Application.Json)
                setBody(request)
            }
            .body()

        return Result.success(response)
    } catch (e: Exception) {
        Log.e("PostRepository", "Error al crear post: ${e.message}")
        return Result.failure(e)
    }
}
💡 Dos cosas nuevas: contentType(ContentType.Application.Json) le dice al servidor que estamos enviando JSON, y setBody(request) agrega el cuerpo de la petición. El try/catch con Result es el mismo patrón que ya conocen.
Detalle técnico

¿Por qué la URL completa esta vez?

Fíjense que en el POST usamos la URL completa:

.post("https://jsonplaceholder.typicode.com/posts")

Mientras que en el GET de TMDB solo escribíamos el endpoint relativo:

.get("movie/popular")

La razón: nuestro KtorClient tiene configurada la URL base de TMDB en el defaultRequest. Como ahora hablamos con otra API (JSONPlaceholder), usamos la URL absoluta para "saltarnos" la base de TMDB en esta llamada.

💡 En proyectos más grandes, cuando hablás con varias APIs, lo profesional es crear un cliente HTTP por cada una. Por hoy, como solo es para aprender POST, alcanza con usar URL absoluta — Ktor ignora la base del defaultRequest cuando ve una URL completa.
ViewModel

El ViewModel — nueva función

Agregamos una función nueva en el ViewModel que recibe el título y el cuerpo, y maneja el resultado con el patrón que ya conocen.

private val _saving = MutableStateFlow(false)
val saving = _saving.asStateFlow()

private val _saveMessage = MutableStateFlow<String?>(null)
val saveMessage = _saveMessage.asStateFlow()

fun createPost(title: String, body: String) {
    viewModelScope.launch {
        _saving.value = true

        postRepository.createPost(title, body)
            .onSuccess { post ->
                _saveMessage.value = "Post creado con ID ${post.id}"
            }
            .onFailure { e ->
                _saveMessage.value = "Error: ${e.message}"
            }

        _saving.value = false
    }
}
💡 Es exactamente el mismo patrón de loadMovies: try/catch encapsulado en el Result, onSuccess y onFailure, un StateFlow para el estado de "guardando". Lo único nuevo es que la función recibe parámetros (el título y el body).
Cierre

¿Qué logramos hoy?

Hoy completamos la mitad que faltaba del consumo de APIs: enviar datos.

✓
Sabemos hacer POST con Ktor — .post(), setBody(), contentType().
✓
Entendemos la diferencia entre DTO de request (lo que enviamos) y DTO de response (lo que recibimos).
✓
El patrón de error handling con Result, onSuccess y onFailure es el mismo que ya conocían.
✓
Sabemos que cuando hablamos con varias APIs, lo profesional es un cliente HTTP por cada una.
💡 Con GET + POST ya tienen los dos métodos HTTP fundamentales. Con eso y la arquitectura que vienen construyendo, pueden hacer prácticamente cualquier app que hable con un servidor.
