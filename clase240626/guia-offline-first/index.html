La app que funciona sin internet

Room como fuente de verdad, sincronizada con la API. Paso a paso sobre la app de películas.

En esta guía vamos a armar el patrón offline-first en la app de películas: Room es la única fuente de verdad, la API solo sirve para sincronizar, y la pantalla sigue mostrando datos aunque no haya señal.

Cómo leer esta guía

Vamos pieza por pieza, de abajo hacia arriba: primero la base de datos, luego el repositorio, y al final los ViewModels y las pantallas. Cada paso muestra el código y explica el porqué.

Al final hay una tarea: aplicar este mismo patrón a RankeUCA.

1El panorama

La regla de oro del offline-first es una sola: la UI siempre lee de Room. La API nunca le habla a la pantalla. Por eso conviene pensarlo como dos caminos separados.

Roomfuente de verdad
→
Repository
→
ViewModelStateFlow
→
UIobserva

Ese es el camino de leer: reactivo, siempre desde Room. Y por aparte, el camino de sincronizar:

APIKtor
→
toEntity()
→
Roomupsert

Cuando sincronizás, Room cambia, y como la UI lo está observando por medio de un Flow, la pantalla se actualiza sola. Sin internet, el camino de sincronizar falla en silencio y el de leer sigue funcionando con la última copia.

Esto nos deja tres formas del mismo dato, cada una con su dueño:

DTO

Lo que viene de la API. Vive en data/api.

Entity

Lo que se guarda en Room. Vive en data/database.

Model

Lo que usa la UI. Vive en model.

2La base de datos: Entity y DAO

Empezamos por abajo. La MovieEntity es la tabla: tiene el id de TMDB como llave primaria (no autogenerada), para que el upsert no duplique al sincronizar.

data/database/entities/MovieEntity.kt
@Entity(tableName = "movies")
data class MovieEntity(
    @PrimaryKey val id: Int,
    val title: String,
    val originalTitle: String,
    val originalLanguage: String,
    val overview: String,
    val releaseDate: String,
    val adult: Boolean,
    val popularity: Double,
    val voteAverage: Double,
    val voteCount: Int,
    val video: Boolean,
    val backdropUrl: String,
    val posterUrl: String
)
Fijate que dejamos genreIds afuera

El modelo Movie tiene un genreIds que es una lista. Room no sabe guardar una List<Int> directo: necesita un TypeConverter, y aprender a guardar este tipo de datos no es parte del scope de esta guía.

Para no enredarnos, lo dejamos fuera de la Entity. Los géneros no se van a persistir, y para lo que estamos viendo está bien. Si te da curiosidad cómo guardar listas en Room, investigá los TypeConverters por tu cuenta.

El DAO expone cuatro cosas: dos para leer (devuelven Flow) y dos para guardar (upsert):

data/database/dao/MovieDao.kt
@Dao
interface MovieDao {

    // Leer: reactivo, la UI observa esto
    @Query("SELECT * FROM movies ORDER BY popularity DESC")
    fun getAll(): Flow<List<MovieEntity>>

    @Query("SELECT * FROM movies WHERE id = :id")
    fun observeById(id: Int): Flow<MovieEntity?>

    // Guardar: insertar o actualizar sin duplicar
    @Upsert
    suspend fun upsert(movie: MovieEntity)

    @Upsert
    suspend fun upsertAll(movies: List<MovieEntity>)
}
Qué hace @Upsert

@Upsert es insertar o actualizar en una sola operación. Room mira la llave primaria: si ya existe una fila con ese id, la actualiza; si no existe, la inserta.

Por eso la llave primaria es el id que viene de TMDB y no una autogenerada: cuando volvés a sincronizar la misma película, se actualiza en su lugar en vez de duplicarse. Sin upsert, cada refresh llenaría la tabla de repetidos.

Por qué Flow en el DAO

El Flow es lo que hace que todo funcione solo: cuando Room cambia (por un upsert), avisa a quien lo esté observando. Sin Flow tendrías que refrescar la pantalla a mano cada vez.

3Los mappers que conectan las capas

Cada salto entre capas tiene su mapper. El primero, toEntity(), pasa del DTO (lo que llega de la API) a la Entity (lo que se guarda). Acá es donde armamos la URL completa de la imagen a partir del path crudo:

data/api/Movies/MovieDto.kt (DTO + mapper)
private const val IMAGE_BASE_URL = "https://image.tmdb.org/t/p/w500"

fun MovieDto.toEntity(): MovieEntity = MovieEntity(
    id = id,
    title = title,
    originalTitle = originalTitle,
    originalLanguage = originalLanguage,
    overview = overview,
    releaseDate = releaseDate,
    adult = adult,
    popularity = popularity,
    voteAverage = voteAverage,
    voteCount = voteCount,
    video = video,
    backdropUrl = backdropPath?.let { "$IMAGE_BASE_URL$it" } ?: "",
    posterUrl = posterPath?.let { "$IMAGE_BASE_URL$it" } ?: ""
)

El segundo, toModel(), pasa de la Entity al modelo de dominio que usa la UI. Como la Entity ya guarda las URLs listas, este mapper solo copia:

data/database/entities/MovieEntity.kt (mapper)
fun MovieEntity.toModel(): Movie = Movie(
    id = id,
    title = title,
    originalTitle = originalTitle,
    originalLanguage = originalLanguage,
    overview = overview,
    releaseDate = releaseDate,
    adult = adult,
    genreIds = emptyList(),   // no lo guardamos en Room (ver nota arriba)
    popularity = popularity,
    voteAverage = voteAverage,
    voteCount = voteCount,
    video = video,
    backdropUrl = backdropUrl,
    posterUrl = posterUrl
)
El camino completo del dato

MovieDto (API) → toEntity() → MovieEntity (Room) → toModel() → Movie (UI). Para guardar usás el primer salto; para leer, el segundo. El modelo de dominio nunca es estación de paso para persistir.

4El KtorClient con base URL

En el Lab pasábamos la URL completa en cada llamada. Acá hacemos algo más cómodo: le ponemos una base URL al cliente, y de paso el token de TMDB. Así en el repositorio escribís solo la ruta relativa (movie/popular).

data/api/KtorClient.kt
object KtorClient {

    private const val BASE_URL = "https://api.themoviedb.org/3/"
    private const val API_TOKEN = "TU_TOKEN_TMDB"   // mejor desde local.properties

    val client = HttpClient(OkHttp) {

        install(ContentNegotiation) {
            json(Json { ignoreUnknownKeys = true })
        }

        install(Logging) {
            logger = object : Logger {
                override fun log(message: String) { Log.d("KtorClient", message) }
            }
            level = LogLevel.ALL
        }

        defaultRequest {
            url(BASE_URL)
            header(HttpHeaders.Accept, "application/json")
            header(HttpHeaders.Authorization, "Bearer $API_TOKEN")
        }
    }
}
Dos detalles que importan

La BASE_URL termina en / y las rutas relativas no empiezan con /. Si invertís eso, Ktor arma mal la URL.

El token no se deja quemado en el código: va en local.properties y se lee desde ahí, como vimos en el Lab.

Acá empieza el corazón. La interfaz ya cuenta la historia con solo mirarla: dos métodos para leer (devuelven Flow, salen de Room) y dos para sincronizar (son suspend, van a la API).

6El repositorio: leer de Room

Leer es siempre lo mismo: agarrás el Flow del DAO y mapeás de Entity a Model. La lista y el detalle siguen el mismo patrón.

MovieOfflineFirstRepositoryImpl.kt (leer)
class MovieOfflineFirstRepositoryImpl(
    private val dao: MovieDao,
) : MovieOfflineFirstRepository {

    // Room manda: la UI siempre observa esto
    override fun getMovies(): Flow<List<Movie>> =
        dao.getAll().map { list -> list.map { it.toModel() } }

    // El detalle también es reactivo y lee de Room
    override fun getMovieById(id: Int): Flow<Movie?> =
        dao.observeById(id).map { it?.toModel() }

    // ... (sincronizar abajo)
}
Fijate lo que NO hay acá

Ni rastro de Ktor ni de la API. Leer es 100% Room. Esa separación es lo que te da el offline gratis.

7El repositorio: sincronizar con la API

Sincronizar es el otro camino: traés los datos de la API (como DTOs), los convertís a Entity y los guardás con upsert. No tocás la UI: el Flow de arriba emite solo con lo nuevo.

MovieOfflineFirstRepositoryImpl.kt (sincronizar)
// Sincroniza la lista: API -> Room (un solo salto de mapeo)
override suspend fun refresh() {
    val popularMovies = fetchPopular()
    dao.upsertAll(popularMovies.map { it.toEntity() })
}

// Sincroniza un detalle puntual: API -> Room
override suspend fun refreshMovieById(id: Int) {
    val movie = fetchById(id)
    dao.upsert(movie.toEntity())
}

// ─── Helpers privados ───
// En un proyecto real vivirían en un MovieRemoteDataSource inyectado.
// Devuelven DTOs: el repositorio decide cómo persistirlos.

private suspend fun fetchPopular(): List<MovieDto> =
    KtorClient.client.get("movie/popular") {
        parameter("language", "es-ES")
        parameter("page", 1)
    }.body<GetMoviesResponseDto>().results

private suspend fun fetchById(id: Int): MovieDto =
    KtorClient.client.get("movie/$id") {
        parameter("language", "es-ES")
    }.body()
Por qué los helpers devuelven DTO

Devuelven MovieDto, no Movie. Así guardás DTO → Entity de un solo salto, sin dar la vuelta por el modelo de dominio. El que decide cómo persistir es el repositorio.

8El cableado: tu turno con el AppProvider

La inyección manual con AppProvider ya la conocés de las clases anteriores: crea la base de datos una sola vez y arma las dependencias para que estén disponibles en toda la app. Acá te toca sumarle la pieza nueva.

Conectá el repositorio

En tu AppProvider, agregá lo necesario para entregar el repositorio offline-first ya armado con su DAO. La Factory del ViewModel lo va a pedir exactamente así:

  • app.appProvider.provideMovieOfflineFirstRepository()

Acordate de crear la base de datos una sola vez (por ejemplo con by lazy) para no abrir varias conexiones.

9El ViewModel de la lista

El ViewModel observa Room con stateIn y dispara la sincronización. Mirá bien el refresh(): el error solo se muestra si Room está vacío.

MovieListViewModel.kt
class MovieListViewModel(
    private val repository: MovieOfflineFirstRepository
) : ViewModel() {

    val movies: StateFlow<List<Movie>> = repository.getMovies()
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

    private val _isRefreshing = MutableStateFlow(false)
    val isRefreshing: StateFlow<Boolean> = _isRefreshing.asStateFlow()

    private val _error = MutableStateFlow<String?>(null)
    val error: StateFlow<String?> = _error.asStateFlow()

    init { refresh() }

    fun refresh() {
        viewModelScope.launch {
            _error.value = null
            _isRefreshing.value = true
            try {
                repository.refresh()
            } catch (_: Exception) {
                // Solo mostramos error si además no hay nada en Room
                if (movies.value.isEmpty()) {
                    _error.value = "Sin conexión y sin datos en caché"
                }
            }
            _isRefreshing.value = false
        }
    }

    companion object {
        val Factory = viewModelFactory {
            initializer {
                val app = this[APPLICATION_KEY] as PDM_Course_2026Application
                MovieListViewModel(app.appProvider.provideMovieOfflineFirstRepository())
            }
        }
    }
}
El detalle que hace offline-first de verdad

Si la API falla pero Room tiene datos, no pasa nada: el usuario sigue viendo sus películas y el error se traga en silencio. El error solo aparece cuando no hay nada que mostrar. Esa decisión es el alma del patrón.

10La pantalla de la lista

La pantalla decide qué mostrar según tres estados. El truco es que el spinner y el error solo salen cuando Room está vacío; si hay cache, siempre se ve la lista.

MovieListScreen.kt (los tres estados)
val movies by viewModel.movies.collectAsState()
val isRefreshing by viewModel.isRefreshing.collectAsState()
val error by viewModel.error.collectAsState()

// 1. Cargando: Room vacío y todavía esperando a la API
if (movies.isEmpty() && isRefreshing) {
    CircularProgressIndicator(...)
    return
}

// 2. Error sin cache: la API falló y no hay nada guardado
if (movies.isEmpty() && error != null) {
    Text("$error")
    Button(onClick = { viewModel.refresh() }) { Text("Reintentar") }
    return
}

// 3. Datos: hay cache (con o sin internet)
PullToRefreshBox(
    isRefreshing = isRefreshing,
    onRefresh = { viewModel.refresh() }
) {
    LazyColumn {
        items(movies) { movie ->
            MovieItem(movie = movie, onClick = { navigateToDetail(movie.id) })
        }
    }
}
Probá el offline acá mismo

Cargá la lista con internet, quitá el wifi y volvé a entrar. Las películas siguen ahí porque salen de Room. Eso es el resultado de todo lo anterior.

11El detalle

El detalle es el mismo patrón, calcado: observa una película de Room y la refresca al entrar. Lo único distinto es que su Factory necesita saber cuál película, así que recibe el movieId.

MovieDetailViewModel.kt
class MovieDetailViewModel(
    private val repository: MovieOfflineFirstRepository,
    private val movieId: Int
) : ViewModel() {

    val movie: StateFlow<Movie?> = repository.getMovieById(movieId)
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), null)

    init { refresh() }

    fun refresh() {
        viewModelScope.launch {
            try {
                repository.refreshMovieById(movieId)
            } catch (e: Exception) {
                // Si falla la API nos quedamos con lo que hay en Room
                e.printStackTrace()
            }
        }
    }

    companion object {
        // Factory con parámetro: assisted injection sin librerías externas
        fun Factory(movieId: Int) = viewModelFactory {
            initializer {
                val app = this[APPLICATION_KEY] as PDM_Course_2026Application
                MovieDetailViewModel(
                    repository = app.appProvider.provideMovieOfflineFirstRepository(),
                    movieId = movieId
                )
            }
        }
    }
}

En la pantalla, la Factory se arma con el movieId que llega por navegación, y se le pasa un key para que cada película tenga su propio ViewModel:

MovieDetailScreenV2.kt (lo esencial)
@Composable
fun MovieDetailScreenV2(
    movieId: Int,
    navigateBack: () -> Unit,
    viewModel: MovieDetailViewModel = viewModel(
        key = movieId.toString(),
        factory = MovieDetailViewModel.Factory(movieId)
    )
) {
    val movie by viewModel.movie.collectAsState()

    if (movie == null) {
        CircularProgressIndicator(...)   // todavía no hay nada en Room
        return
    }

    movie?.let {
        // Acá va tu UI: hero, stats, géneros, sinopsis...
    }
}
Por qué el key en el viewModel()

El key = movieId.toString() le dice a Compose que cada película tiene su propio ViewModel. Sin eso, al pasar de una peli a otra te quedarías viendo la anterior.

12Checkpoint

Antes de la tarea, asegurate de que tu app hace todo esto:

Deberías tener funcionando

• La lista carga las películas y las guarda en Room.
• Con el wifi apagado, la lista y el detalle siguen mostrando lo último que cargaste.
• El pull-to-refresh baja datos nuevos y la pantalla se actualiza sola.
• Si entrás por primera vez sin internet, ves el mensaje de error con Reintentar.

13Tu turno: RankeUCA offline-first

Ahora aplicás el mismo patrón a RankeUCA. La idea de fondo es idéntica, pero con dos vueltas de tuerca: RankeUCA tiene preguntas y opciones, y además se pueden crear, editar y eliminar.

Lo que se mantiene igual

Room sigue siendo la fuente de verdad para leer. La UI lee las preguntas y las opciones de Room, con Flow. Y refresh() sigue trayendo todo de la API y guardándolo con upsert.

APIGET
→
toEntity()
→
Roomupsert
→
UIobserva

Lo nuevo: las mutaciones

Crear, editar y eliminar no tocan Room directo. Le apuntan a la API. Y solo cuando la API responde bien, refrescás Room para que la pantalla refleje el cambio.

UIcrear / editar / borrar
→
Repository
→
APIPOST/PUT/DELETE
→
refresh()
→
Room
El orden importa

Primero la API, y solo si sale bien, refrescás Room. Si la API falla, no tocás Room: así la pantalla nunca queda mostrando algo que el servidor no aceptó.

Lo que tenés que entregar

Una versión de RankeUCA donde:

  • La UI lee las preguntas y sus opciones desde Room (Flow).
  • Un refresh() sincroniza preguntas y opciones desde la API hacia Room.
  • Crear, editar y eliminar (preguntas y opciones) le pegan a la API y, tras el éxito, refrescan Room.

Acordate de la relación uno a muchos del Taller 3: cada opción lleva su questionId.

Como punto de partida, esta es la forma que debería tener tu interfaz. La implementación es tuya:

QuestionOfflineFirstRepository.kt (esqueleto sugerido)
interface QuestionOfflineFirstRepository {

    // Leer: de Room (fuente de verdad)
    fun getQuestions(): Flow<List<Question>>
    fun getOptions(questionId: Int): Flow<List<Option>>

    // Sincronizar: API -> Room
    suspend fun refresh()

    // Mutar: API -> luego refresh()
    suspend fun createQuestion(text: String)
    suspend fun updateQuestion(id: Int, text: String)
    suspend fun deleteQuestion(id: Int)

    suspend fun createOption(questionId: Int, value: String)
    suspend fun updateOption(id: Int, value: String)
    suspend fun deleteOption(id: Int)
}
La API

Los endpoints están documentados acá:

https://qjcxdvfzyseuvezacxsd.supabase.co/functions/v1/rankeuca/docs

Parte del ejercicio es leer la documentación: identificá cuáles endpoints son para traer (GET), crear (POST), editar (PUT o PATCH) y eliminar (DELETE), tanto para preguntas como para opciones, y qué datos pide cada uno.

Pistas
  • El upsert es tu amigo al sincronizar: inserta lo nuevo y actualiza lo que ya estaba, sin duplicar.
  • Una mutación es siempre el mismo libreto: llamás a la API, y si responde bien, refresh(). El Flow hace el resto.
  • El manejo de error va en el ViewModel con try/catch, igual que en las películas.
  • Para sincronizar las opciones junto con las preguntas, pensá si las traés todas de una o por pregunta. Las dos formas son válidas; elegí y justificá.
Puntos de aceptación

Tu entrega está lista cuando:

• Sin internet, la app muestra las preguntas y opciones que ya estaban en Room.
• Al refrescar con internet, los datos se actualizan solos.
• Crear, editar y eliminar le pegan a la API y, tras el éxito, la pantalla refleja el cambio.
• La UI nunca lee de la API directo: siempre de Room.

Reto extra (opcional)

¿Qué pasa si alguien intenta crear, editar o eliminar sin internet?

La solución completa sería guardar esa acción en local y mandarla a la API cuando vuelva la señal, o sea una cola de cambios pendientes que se sincroniza sola. Eso es bastante más avanzado y tampoco es parte del scope de esta clase. Si te llama la atención, podés intentarlo por tu cuenta.

Por ahora, en lo que sí nos vamos a quedar es en lo más simple y honesto: avisarle al usuario que esa acción necesita conexión, sin que la app truene. Por ejemplo, si la mutación falla por falta de internet, mostrá un mensaje claro y no toques Room.
