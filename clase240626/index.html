La pregunta

Toda app necesita datos

La pregunta de fondo siempre es la misma: ¿de dónde sale la verdad? O sea, ¿cuál es la fuente confiable de la que la app saca lo que muestra.

💡 Hoy vamos a ver que hay tres respuestas, y que el repositorio se adapta a cada una.

Dos ya las conocen. La tercera es la de hoy.

Opción 1 · ya la vimos

Solo la API

Cuándo: cuando siempre querés lo más fresco y no tiene sentido guardar nada: una búsqueda, una cotización en vivo, el clima, el marcador de un partido, el estado de un vuelo, el rastreo de un envío o la disponibilidad de un Uber.

El patrón: Ktor + Result. El repositorio le pide a la API y devuelve el resultado. Esto es el Lab.

💡 Sin internet: no hay nada que mostrar.

El patrón: Room + DAO con Flow. El repositorio lee y escribe en Room. Esto son los talleres.

💡 No necesita internet nunca.
El escenario que falta

¿Y si viene de la API pero no hay señal?

Con la opción 1, el dato vive en el servidor. Perfecto cuando hay internet. Pero el día que no hay señal, la pantalla queda vacía.

Vas en el bus sin datos, abrís la app de películas y no ves ni un afiche, aunque hace cinco minutos ya habías cargado la cartelera.

💡 Acá aparece una tercera opción: traer de la API, pero guardarlo para que siga estando sin internet.

Concepto

Single Source of Truth

💡 La UI siempre lee de Room. Room es el que manda.

Ktor no le habla a la pantalla. Solo se encarga de mantener Room actualizado. Cuando Room cambia, le avisa a la UI por medio de un Flow.

El hilo en común

El repositorio se adapta, la idea es la misma

En las tres opciones, la UI hace exactamente lo mismo: le pide los datos al repositorio. La UI no sabe ni le importa de dónde salen.

El que decide es el repositorio: si pide a la API, si lee de Room, o si hace las dos cosas. Lo único que cambia entre opciones es esa implementación de adentro.

💡 Esa es la gracia del patrón Repository: cambiás la fuente sin tocar la UI.
Para que haga clic

Los superpoderes del offline

Hagan la prueba: quiten el wifi y abran Facebook o Twitter. Igual les salen los últimos posts que ya habían cargado.

💡 Eso es Room como fuente de verdad: los posts ya estaban guardados, así que la app los muestra aunque no haya señal.

Casi todas las apps que usan a diario funcionan así. Y eso es justo lo que vamos a construir.

El código · 1

La interfaz: leer y sincronizar

interface MovieOfflineFirstRepository {

    // Leer: salen de Room, son reactivos (Flow)
    fun getMovies(): Flow<List<Movie>>
    fun getMovieById(id: Int): Flow<Movie?>

    // Sincronizar: van a la API y guardan en Room
    suspend fun refresh()
    suspend fun refreshMovieById(id: Int)
}
💡 La forma de la interfaz ya cuenta la historia: dos métodos para leer (Flow, de Room) y dos para sincronizar (suspend, de la API).
El código · 2

El repositorio: leer siempre de Room

// Lista
override fun getMovies(): Flow<List<Movie>> =
    dao.getAll().map { list -> list.map { it.toModel() } }

// Detalle (el mismo patrón)
override fun getMovieById(id: Int): Flow<Movie?> =
    dao.observeById(id).map { it?.toModel() }
💡 Leer es siempre lo mismo: un Flow que sale de Room y convierte Entity → Model. La UI observa esto y se actualiza sola.
El código · 3

El repositorio: sincronizar API → Room

override suspend fun refresh() {
    val popular = fetchPopular()                  // trae DTOs de la API
    dao.upsertAll(popular.map { it.toEntity() })  // los guarda en Room
}

private suspend fun fetchPopular(): List<MovieDto> =
    KtorClient.client.get("movie/popular") {
        parameter("language", "es-ES")
        parameter("page", 1)
    }.body<GetMoviesResponseDto>().results
💡 Sincronizar no toca la UI: solo trae DTOs y hace upsert. El Flow de getMovies() emite solo con los datos nuevos.
El código · 4

El ViewModel: observar y refrescar

val movies: StateFlow<List<Movie>> = repository.getMovies()
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), emptyList())

init { refresh() }

fun refresh() {
    viewModelScope.launch {
        _error.value = null
        _isRefreshing.value = true
        try {
            repository.refresh()
        } catch (_: Exception) {
            if (movies.value.isEmpty()) {
                _error.value = "Sin conexión y sin datos en caché"
            }
        }
        _isRefreshing.value = false
    }
}
💡 El error solo aparece si Room está vacío. Si ya hay cache, un fallo de red es silencioso: el usuario sigue viendo sus películas. Eso es offline-first.
El código · 5

La pantalla: tres estados

// 1. Cargando: Room vacío y todavía esperando a la API
if (movies.isEmpty() && isRefreshing) { /* spinner */ }

// 2. Error sin cache: la API falló y no hay nada guardado
if (movies.isEmpty() && error != null) { /* mensaje + Reintentar */ }

// 3. Datos: hay cache (con o sin internet)
PullToRefreshBox(isRefreshing, onRefresh = { refresh() }) {
    LazyColumn { items(movies) { MovieItem(it) } }
}

El spinner y el error solo salen cuando no hay nada que mostrar. Si hay cache, siempre se ve la lista.

El detalle: el mismo patrón

val movie: StateFlow<Movie?> = repository.getMovieById(movieId)
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), null)

init { refresh() }   // refresh() llama a refreshMovieById(movieId)

// La Factory recibe el id de la película
fun Factory(movieId: Int) = viewModelFactory {
    initializer {
        MovieDetailViewModel(repository, movieId)
    }
}
💡 Idéntico a la lista: observa Room, refresca al entrar. La Factory recibe el id (assisted injection, sin librerías extra).
