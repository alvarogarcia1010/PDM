La API

¿Qué es una API?

Una API es un servicio en internet que devuelve datos cuando se los pedís. Tu app le hace una petición y la API le responde — normalmente en formato JSON.

Tu app
── petición (GET) ──▶
API de TMDB
Tu app
◀── respuesta (JSON) ──
API de TMDB
La app pide, la API responde. Toda la comunicación viaja por internet.
Endpoint: una URL específica para pedir algo concreto.
JSON: el formato de texto en que viaja la respuesta.
Token: la credencial que nos identifica ante la API.
💡 Vamos a usar TMDB (The Movie Database), una API pública con información de miles de películas. Saber explorar y entender una API es clave: te deja probar endpoints, entender la respuesta antes de programar y depurar cuando algo falla.
La API

El endpoint y su respuesta

El endpoint de películas populares se ve así:

GET https://api.themoviedb.org/3/movie/popular?language=es-SV&page=1

Y nos responde un JSON con esta forma:

{
  "page": 1,
  "results": [
    { "id": 552524, "title": "Lilo & Stitch", "vote_average": 7.1 },
    { "id": 1234821, "title": "Jurassic World", "vote_average": 7.2 }
  ],
  "total_pages": 51242
}
💡 La respuesta tiene un envoltorio: el objeto principal trae page, total_pages y un array results con las películas adentro.
Preparación · 1/2

Las dependencias — el catálogo

Para hablar con la API usamos Ktor, el cliente HTTP de Kotlin. Primero declaramos las versiones y librerías en el libs.versions.toml.

[versions]
ktor = "3.4.3"

[libraries]
ktor-client-core = { group = "io.ktor", name = "ktor-client-core", version.ref = "ktor" }
ktor-client-okhttp = { group = "io.ktor", name = "ktor-client-okhttp", version.ref = "ktor" }
ktor-client-content-negotiation = { group = "io.ktor", name = "ktor-client-content-negotiation", version.ref = "ktor" }
ktor-serialization-kotlinx-json = { group = "io.ktor", name = "ktor-serialization-kotlinx-json", version.ref = "ktor" }
ktor-client-logging = { group = "io.ktor", name = "ktor-client-logging", version.ref = "ktor" }
💡 El libs.versions.toml es el catálogo de dependencias del proyecto. Acá se declara todo una sola vez, y se referencia desde cualquier módulo. Las 5 librerías de Ktor usan la misma versión ktor.
Preparación · 2/2

Las dependencias — usarlas

Ya declaradas en el catálogo, las referenciamos en el build.gradle.kts del módulo :app.

// build.gradle.kts (Module :app)

dependencies {
    implementation(libs.ktor.client.core)
    implementation(libs.ktor.client.okhttp)
    implementation(libs.ktor.client.content.negotiation)
    implementation(libs.ktor.serialization.kotlinx.json)
    implementation(libs.ktor.client.logging)
}

El plugin de serialización ya lo tenemos del proyecto. Después de agregar esto, sincronizá Gradle.

💡 El permiso de internet ya lo tenemos en el Manifest desde que agregamos Coil. Si no estuviera, habría que agregarlo: <uses-permission android:name="android.permission.INTERNET"/>
DTOs

¿Qué es un DTO?

Un DTO (Data Transfer Object) es una clase que representa exactamente lo que la API nos devuelve. Es el "molde" del JSON.

✓
El DTO hace match exacto con el JSON: nombres, tipos, estructura externa.
✓
El Modelo es lo que tu app usa: limpio, con solo lo que necesitás.
💡 Si TMDB cambia un nombre de campo, solo tocás el DTO y el mapper. El resto de la app ni se entera. El DTO aísla a la app de los cambios de la API.
DTOs

Los DTOs de la lista

Necesitamos dos: uno para el envoltorio y otro para cada película.

@Serializable
data class GetMoviesResponseDto(
    val page: Int,
    val results: List<MovieDto>,
    @SerialName("total_pages") val totalPages: Int,
    @SerialName("total_results") val totalResults: Int
)

@Serializable
data class MovieDto(
    val id: Int,
    val title: String,
    @SerialName("original_title") val originalTitle: String,
    @SerialName("original_language") val originalLanguage: String,
    val overview: String,
    @SerialName("release_date") val releaseDate: String,
    val adult: Boolean,
    val popularity: Double,
    @SerialName("vote_average") val voteAverage: Double,
    @SerialName("vote_count") val voteCount: Int,
    val video: Boolean,
    @SerialName("backdrop_path") val backdropPath: String?,
    @SerialName("poster_path") val posterPath: String?
)
💡 @Serializable habilita la clase para convertirse desde JSON. @SerialName mapea nombres: la API usa vote_average, nosotros usamos voteAverage. Los campos de imagen son String? porque pueden venir nulos.
DTOs

El Mapper — de DTO a Modelo

Una función de extensión convierte el MovieDto al modelo Movie que usa la app.

private const val IMAGE_BASE_URL = "https://image.tmdb.org/t/p/w500"

fun MovieDto.toModel(): Movie {
    return Movie(
        id = id,
        title = title,
        originalTitle = originalTitle,
        originalLanguage = originalLanguage,
        overview = overview,
        releaseDate = releaseDate,
        adult = adult,
        genreIds = emptyList(),
        popularity = popularity,
        voteAverage = voteAverage,
        voteCount = voteCount,
        video = video,
        backdropUrl = backdropPath?.let { "$IMAGE_BASE_URL$it" } ?: "",
        posterUrl = posterPath?.let { "$IMAGE_BASE_URL$it" } ?: ""
    )
}
💡 fun MovieDto.toModel() es una función de extensión: le "agrega" el método toModel() a la clase MovieDto sin modificar la clase original. Por eso después podés escribir dto.toModel() como si fuera un método propio del DTO. Dentro de la función, id, title, etc. se refieren a las propiedades del DTO sobre el que se llama.
Ktor Client

Configurar el cliente Ktor

El KtorClient es un object — una sola instancia para toda la app. Acá se configura todo.

object KtorClient {

    private const val BASE_URL = "https://api.themoviedb.org/3/"
    private const val BEARER_TOKEN = "..." // el token de TMDB

    val client = HttpClient(OkHttp) {

        // Parseo automático de JSON
        install(ContentNegotiation) {
            json(Json {
                ignoreUnknownKeys = true
            })
        }

        // Configuración para todas las peticiones
        defaultRequest {
            url(BASE_URL)
            header(HttpHeaders.Authorization, "Bearer $BEARER_TOKEN")
            header(HttpHeaders.Accept, "application/json")
        }
    }
}
💡 ContentNegotiation convierte el JSON automáticamente. ignoreUnknownKeys es clave: TMDB manda muchos campos que no usamos — sin esto, la app crashea. defaultRequest aplica la URL base y el token a todas las llamadas.
Ktor Client

Ver qué responde la API — Logging

Ktor tiene un plugin que registra cada petición y respuesta en el Logcat. Útil para entender y depurar.

install(Logging) {
    logger = object : Logger {
        override fun log(message: String) {
            Log.d("KtorClient", message)
        }
    }
    level = LogLevel.ALL
}
✓
Filtrando por KtorClient en el Logcat ven cada llamada y la respuesta completa.
✓
Cuando algo falle, el log dice qué pasó: el código de error, el cuerpo de la respuesta.
💡 Ojo: LogLevel.ALL muestra hasta el token en el Logcat. Para aprender está bien, pero en una app publicada el logging se baja a INFO o se apaga — las credenciales no deben quedar en los logs.
Repository

El Repository con Ktor

Ahora la implementación del Repository hace la llamada real a la API.

class MovieApiRepository : MovieRepository {

    override suspend fun getMovies(): List<Movie> {
        // 1. Petición GET al endpoint
        val response: GetMoviesResponseDto = KtorClient.client
            .get("movie/popular") {
                parameter("language", "es-SV")
                parameter("page", 1)
            }
            .body()

        // 2. Convertimos los DTOs al modelo de dominio
        return response.results.map { apiMovie ->
            apiMovie.toModel()
        }
    }
}
💡 Como la URL base está en el defaultRequest, acá solo escribimos el endpoint: "movie/popular". parameter() arma los query params, y .body() convierte la respuesta al DTO. Sigue siendo suspend — la llamada de red toma tiempo.
El valor de MVVM

Lo que NO cambió

Pasamos de datos hardcoded a una API real. ¿Cuánto código tuvimos que tocar fuera de la capa de datos?

Lo que cambió

Solo la capa de datos: creamos los DTOs, el KtorClient y una nueva implementación del Repository.

Lo que NO cambió

El ViewModel sigue igual. La View sigue igual. La interface MovieRepository sigue igual.

💡 Esto es exactamente lo que prometimos cuando hicimos MVVM y Repository. El cambio se localiza en una sola capa. El resto de la app ni se enteró. Por esto vale la pena la arquitectura.
Repository

Segundo endpoint: detalle por ID

Para traer una sola película, el id va en la ruta, no como query param.

override suspend fun getMovieById(id: Int): Movie {
    val response: MovieDto = KtorClient.client
        .get("movie/$id") {
            parameter("language", "es-SV")
        }
        .body()

    return response.toModel()
}
💡 La diferencia clave: el id se interpola en la ruta con $id. Los parameter() son solo para lo que va después del ?. Y este endpoint devuelve la película directa — sin envoltorio results.
Cuando algo falla

Errores comunes

Consumir una API es la primera vez que el código depende de algo externo. Estos errores son normales — lo importante es saber leerlos.

401 Unauthorized
Causa: el token está mal o le falta Bearer adelante. Revisá el header Authorization.
SerializationException: Field 'X' is required
Causa: un campo del DTO vino null pero no es nullable. Solución: hacé ese campo String?.
UnknownHostException
Causa: no hay internet, o falta el permiso INTERNET en el Manifest.
La app crashea al parsear el JSON
Causa: falta ignoreUnknownKeys = true en la config del Json.
💡 El plugin de Logging es tu mejor amigo acá: el log te dice el código de error y la respuesta exacta de la API.
Buenas prácticas

El token no debe ir en el código

Hasta ahora el token está hardcoded en el KtorClient. Si subís el código a GitHub, tu token queda público. La solución: guardarlo en local.properties, que nunca se sube.

1
En local.properties (raíz del proyecto) agregás: TMDB_TOKEN=tu_token_aqui  — sin comillas.
2
En build.gradle.kts leés el archivo y exponés el valor vía BuildConfig.
3
En el KtorClient usás BuildConfig.TMDB_TOKEN en lugar del texto hardcoded.
// build.gradle.kts (:app) — arriba del bloque android { }
import java.util.Properties
import java.io.FileInputStream

val localProperties = Properties()
val localPropertiesFile = rootProject.file("local.properties")
if (localPropertiesFile.exists()) {
    localProperties.load(FileInputStream(localPropertiesFile))
}
val tmdbToken: String = localProperties.getProperty("TMDB_TOKEN") ?: ""

android {
    defaultConfig {
        buildConfigField("String", "TMDB_TOKEN", "\"$tmdbToken\"")
    }
    buildFeatures { buildConfig = true }
}
💡 Ojo: local.properties NO es un archivo de propiedades de Gradle — por eso hay que leerlo a mano con Properties(). Ya está en el .gitignore por defecto, así que tu token nunca llega a GitHub. Cada quien pone el suyo.
Lo que viene

Ya consumimos datos reales

Hoy la app trae películas reales desde internet. Pero hay un detalle: cada vez que entran a la pantalla, se vuelve a llamar a la API.

Aunque ya hayamos traído esas películas hace un minuto, las pedimos de nuevo. Eso gasta datos, batería, y hace la app más lenta.
