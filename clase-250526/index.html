Manejar errores y recarga de datos

Cuando la API falla y cómo dejar que el usuario reintente

"Una app que crashea es peor que una app que muestra un error"

Docente: Alvaro García

Recordatorio

¿Dónde quedamos?

La clase pasada conectamos la app a una API real con Ktor. La app trae películas desde TMDB y se ven en pantalla.

Pero hay un detalle: todo eso depende de que haya internet y de que la API responda. ¿Qué pasa si algo de eso falla?

💡 Spoiler: la app crashea. Hoy vamos a ver cómo evitarlo, y de paso le damos al usuario una forma de reintentar con pull-to-refresh.
El problema

Sin internet, la app crashea

Prueben esto: pongan el celular en modo avión y abran la app. Esto es lo que pasa:

FATAL EXCEPTION: main
Process: com.agarcia.pdm_course_2026, PID: 12384
java.net.UnknownHostException: Unable to resolve host
  "api.themoviedb.org": No address associated with hostname
  at java.net.Inet6AddressImpl.lookupHostByName(...)
  at io.ktor.client.engine.okhttp.OkHttpEngine...
  at com.agarcia.pdm_course_2026...MovieApiRepository.getMovies(...)
💡 La llamada a la API lanza una excepción nadie la atrapa, y sube hasta crashear la app. El problema no es la API — es que no manejamos el error.
Result<T>

Result<T> — el tipo que dice "éxito o fracaso"

Kotlin tiene una clase llamada Result<T> que representa un resultado que puede ser exitoso o fallido.

// Crear un éxito
val exito: Result<List<Movie>> = Result.success(listOf(...))

// Crear un fallo
val fallo: Result<List<Movie>> = Result.failure(Exception("Sin internet"))

// Y para usarlo, dos métodos clave:
resultado
    .onSuccess { datos -> /* hacé algo con los datos */ }
    .onFailure { error -> /* mostrá el mensaje del error */ }
💡 En lugar de lanzar excepciones que crashean, el Repository devuelve un Result. El ViewModel revisa si fue éxito o fracaso y reacciona. Nada crashea — todo se maneja con código normal.
Repository

El Repository devuelve Result

Cambiamos la firma del Repository: ya no devuelve List<Movie>, ahora devuelve Result<List<Movie>>. Adentro, un try/catch atrapa cualquier excepción.

interface MovieRepository {
    suspend fun getMovies(): Result<List<Movie>>
    suspend fun getMovieById(id: Int): Result<Movie>
}

class MovieApiRepository : MovieRepository {

    override suspend fun getMovies(): Result<List<Movie>> {
        try {
            val response: GetMoviesResponseDto = KtorClient.client
                .get("movie/popular") {
                    parameter("language", "es-SV")
                    parameter("page", 1)
                }
                .body()

            return Result.success(response.results.map { it.toModel() })
        } catch (e: Exception) {
            Log.e("MovieApiRepository", "Error al obtener películas: ${e.message}")
            return Result.failure(e)
        }
    }
}
💡 Si la llamada funciona, devolvemos Result.success con los datos. Si cualquier cosa falla (sin internet, JSON malo, error del servidor), el catch la atrapa, lo loguea con Log.e para poder depurar, y devuelve Result.failure. El mismo patrón se aplica a getMovieById — solo cambia el tipo a Result<Movie>.
ViewModel

El ViewModel reacciona al Result

El ViewModel ya tenía los StateFlow de movies y loading. Solo agregamos uno nuevo para el error, y reescribimos loadMovies() para manejar el Result.

// Nuevo StateFlow para el error
private val _error = MutableStateFlow<String?>(null)
val error = _error.asStateFlow()

// loadMovies actualizado
fun loadMovies() {
    viewModelScope.launch {
        _loading.value = true
        _error.value = null

        movieRepository.getMovies()
            .onSuccess { movies -> _movies.value = movies }
            .onFailure { e -> _error.value = e.message }

        _loading.value = false
    }
}
💡 onSuccess y onFailure son los dos métodos clave de Result: el primero se ejecuta si todo salió bien, el segundo si hubo error. Antes de cada carga limpiamos el error con _error.value = null para no mostrar errores viejos cuando el usuario reintenta.
Estados de UI

Toda pantalla con datos tiene 3 estados

Este es un patrón clásico de Android — vale la pena tenerlo claro porque lo van a usar en todas sus apps.

⏳
Cargando
Mostrar un indicador mientras llegan los datos.
⚠️
Error
Algo falló. Mostrar un mensaje claro y opcionalmente un botón para reintentar.
✅
Éxito
Los datos llegaron. Mostrar la lista normalmente.
💡 La View pregunta en este orden: ¿está cargando? Mostrá el spinner. ¿Hay error? Mostrá el mensaje. Si no, mostrá los datos. Cada estado tiene su UI propia.
View

Lo nuevo en la View — el bloque de error

El Composable ya manejaba loading y los datos. Solo agregamos el bloque del error: si error no es nulo, mostramos el mensaje y un botón para reintentar.

val error by viewModel.error.collectAsState()

if (error != null) {
    AppScaffold(title = "Movies") { padding ->
        Column {
            Text(
                text = error ?: "Unknown error",
                modifier = Modifier.padding(padding)
            )
            Button(onClick = { viewModel.loadMovies() }) {
                Text("Reintentar")
            }
        }
    }
    return
}
💡 El return corta acá — si hay error, no se ejecuta el resto del Composable. El botón vuelve a llamar a loadMovies(), que ya sabe limpiar el error antes de hacer la nueva petición.

Recargar datos

¿Y si el usuario quiere ver lo nuevo?

Ya manejamos los errores. Pero pensemos en este escenario:

→

El usuario abre la app y la lista de películas se carga bien.

→

Pasan unos minutos. Quizás TMDB ya tiene películas nuevas en el catálogo.

→

¿Cómo hace el usuario para decirle a la app "recargá, traé lo último"?

Hay un patrón estándar que los usuarios esperan en cualquier app moderna: deslizar hacia abajo para recargar.

💡 Es el pull-to-refresh: el usuario tira hacia abajo, aparece un indicador girando, y la pantalla se recarga. Lo ven en Instagram, Twitter, Gmail, todas las apps.
Pull-to-refresh

PullToRefreshBox de Material 3

Material 3 trae un componente listo: PullToRefreshBox. Lo envolvemos alrededor de la lista y queda funcionando.

val refreshing by viewModel.refreshing.collectAsState()

PullToRefreshBox(
    onRefresh = { viewModel.refreshMovies() },
    isRefreshing = refreshing,
    modifier = Modifier
        .fillMaxSize()
        .padding(padding)
        .padding(16.dp),
) {
    LazyColumn {
        items(movies) { movie ->
            MovieItem(
                movie = movie,
                onClick = { navigateToDetail(movie.id) }
            )
            Spacer(modifier = Modifier.height(12.dp))
        }
    }
}
💡 Dos parámetros: isRefreshing le dice al componente si mostrar el indicador girando, y onRefresh es lo que se ejecuta cuando el usuario suelta el dedo. Usamos un StateFlow aparte para refreshing — distinto del loading de la primera carga.
Cierre

¿Qué logramos hoy?

Empezamos con una app que crashea sin internet. Terminamos con una app que se comporta como una app real.

✓
No crashea. Cualquier error de la API se atrapa con try/catch.
✓
Le habla al usuario. Si algo falla, ve un mensaje claro y un botón para reintentar.
✓
Los 3 estados se manejan limpio. Loading, error y éxito tienen su UI propia.
✓
El usuario puede recargar. Pull-to-refresh es el patrón estándar y ahora la app lo tiene.
💡 Y todo esto sin romper la arquitectura: el Repository sigue siendo Repository, el ViewModel sigue siendo ViewModel. Solo cambiamos el tipo de retorno a Result y agregamos un estado de error.
