El problema

Los datos no son hardcoded en la vida real

Hasta ahora teníamos los datos así:

// data/DummyMovies.kt
val dummyMovies = listOf(
    Movie("Minecraft", 9.0),
    Movie("Dune", 8.7),
    Movie("Interstellar", 9.3)
)

Pero en una app real los datos vienen de afuera. ¿De dónde?

→
Una API — un servidor en internet que devuelve datos.
→
Una base de datos local — guardada en el celular.
→
Archivos del dispositivo, caché, o varios a la vez.
💡 Si el ViewModel sabe directamente de dónde vienen los datos, se acopla a esa fuente. Cambiarla después se vuelve un infierno.
Capa de Datos

Capa de Datos

La capa de datos contiene la lógica empresarial. Esta lógica es lo que le da valor a la app, y está compuesta por reglas que determinan cómo la app crea, almacena y cambia datos.

Está formada por repositorios que pueden contener de cero a muchas fuentes de datos. Por ejemplo, una clase MoviesRepository para datos de películas o PaymentsRepository para datos de pagos.

Repository

Interface + Implementación

Definimos primero una interface que dice "qué se puede hacer", y después una implementación que dice "cómo se hace".

// data/repository/MovieRepository.kt
interface MovieRepository {
    suspend fun getMovies(): List<Movie>
}

// data/repository/MovieRepositoryImpl.kt
class MovieRepositoryImpl : MovieRepository {
    override suspend fun getMovies(): List<Movie> {
        delay(2000) // simula que tarda 2 segundos
        return dummyMovies
    }
}
💡 La interface es el contrato: lo que se promete. La implementación es cómo se cumple esa promesa. Si mañana cambiamos a Ktor, solo creamos otra implementación. La interface no se toca.
Corrutinas

La palabra suspend

Fíjense en la firma de la función:

suspend fun getMovies(): List<Movie>

La palabra suspend indica que la función puede tomar tiempo. Por ejemplo, una llamada a internet puede tardar 2 segundos en responder.

✓
No bloquea el hilo principal. Mientras espera la respuesta, la app sigue respondiendo a clicks y animaciones.
✓
Solo se puede llamar desde una corrutina u otra función suspend. Es una regla de Kotlin.
💡 Sin suspend, si la API tarda 5 segundos, la app se congela 5 segundos. Con suspend, la espera es asíncrona y la UI sigue fluida.
Corrutinas

¿Cómo llamamos una función suspend?

Una función suspend solo se puede llamar desde dentro de una corrutina. En el ViewModel, las corrutinas se crean con viewModelScope.launch.

fun loadMovies() {
    viewModelScope.launch {
        // adentro del launch sí podemos llamar funciones suspend
        val movies = movieRepository.getMovies()
        _movies.value = movies
    }
}
✓
viewModelScope está atado al ciclo de vida del ViewModel. Si el ViewModel se destruye, la corrutina se cancela automáticamente.
✓
launch inicia la corrutina y libera el hilo. El código de adentro corre "en paralelo" sin bloquear nada.
💡 Sin viewModelScope.launch, no podemos llamar suspend fun getMovies(). Es la "puerta de entrada" al mundo asíncrono desde el ViewModel.
Implementación

El ViewModel actualizado

Ahora el ViewModel le pide los datos al Repository. Mientras llegan, expone un estado de loading para que la View muestre un indicador.

// screens/MovieList/MovieListViewModel.kt
class MovieListViewModel : ViewModel() {

    val movieRepository: MovieRepository = MovieRepositoryImpl()

    private val _movies = MutableStateFlow<List<Movie>>(emptyList())
    val movies = _movies.asStateFlow()

    private val _loading = MutableStateFlow(false)
    val loading = _loading.asStateFlow()

    fun loadMovies() {
        viewModelScope.launch {
            _loading.value = true
            _movies.value = movieRepository.getMovies()
            _loading.value = false
        }
    }
}
💡 Tres estados expuestos: lista vacía al inicio, loading en true mientras carga, y la lista llena cuando llegan los datos. La View no necesita saber nada del Repository.
Implementación

La View actualizada

Ahora la View también observa el estado de loading y muestra un indicador mientras llegan los datos.

// screens/MovieList/MovieListScreen.kt
@Composable
fun MovieListScreen(
    viewModel: MovieListViewModel = viewModel()
) {
    val movies by viewModel.movies.collectAsState()
    val loading by viewModel.loading.collectAsState()

    if (loading) {
        CircularProgressIndicator()
        return
    }

    LazyColumn {
        items(movies) { movie ->
            Text("${movie.title} - ${movie.rating}")
        }
    }
}
💡 La View sigue siendo simple: solo observa estado y muestra UI. Si carga, muestra indicador. Si no, muestra la lista. Sin lógica de carga.
Pregunta clave

¿Quién dispara loadMovies()?

Tenemos el ViewModel listo. Tenemos la View lista. Pero nadie está llamando a loadMovies(). La función existe, pero nadie la ejecuta.

Hay dos formas de hacerlo, y cada una tiene su uso. Vamos a verlas las dos.

💡 Esta decisión parece pequeña pero tiene impacto: define cuándo se ejecuta la carga y quién tiene el control.
Opción 1

Cargar desde el init del ViewModel

El ViewModel dispara la carga apenas se crea. Se hace en el bloque init.

class MovieListViewModel : ViewModel() {

    private val _movies = MutableStateFlow<List<Movie>>(emptyList())
    val movies = _movies.asStateFlow()

    init {
        loadMovies()  // ← se llama al crear el ViewModel
    }

    fun loadMovies() {
        viewModelScope.launch {
            _movies.value = movieRepository.getMovies()
        }
    }
}
💡 La carga ocurre cuando el ViewModel se crea. Como el ViewModel sobrevive a la rotación, la carga no se repite. Funciona, pero la View no tiene control sobre cuándo cargar.
Opción 2

Cargar desde la View con LaunchedEffect

La View le avisa al ViewModel "cargá los datos" cuando la pantalla aparece. Se hace con LaunchedEffect.

@Composable
fun MovieListScreen(
    viewModel: MovieListViewModel = viewModel()
) {
    val movies by viewModel.movies.collectAsState()

    LaunchedEffect(Unit) {
        viewModel.loadMovies()  // ← se llama al entrar a la pantalla
    }

    LazyColumn { /* ... */ }
}
💡 LaunchedEffect(Unit) ejecuta el bloque una sola vez cuando el composable aparece. Coherente con el flujo unidireccional: la View envía un evento ("cargá") al ViewModel.
Comparación

¿Cuál usar?

📦 init del ViewModel
✓ Se ejecuta una sola vez en la vida del ViewModel
✓ Sobrevive a rotación Y navegación
✓ Más simple de escribir
✗ Difícil si la carga depende de parámetros
🎯 LaunchedEffect
✓ La View controla cuándo cargar
✓ Funciona con parámetros: LaunchedEffect(id)
✗ Se vuelve a disparar al volver a la pantalla
✗ Puede causar recargas innecesarias
💡 Las dos funcionan. Por defecto usen init porque es más seguro: el ViewModel se crea una sola vez, así que la carga ocurre una sola vez. Usen LaunchedEffect cuando la carga dependa de un parámetro que pueda cambiar (ejemplo: cargar el detalle de una película según su ID).
Cierre

¿Qué ganamos con la Capa de Datos?

Comparemos con lo que teníamos al inicio de la clase pasada.

✓
El ViewModel no sabe de dónde vienen los datos — solo se los pide al Repository.
✓
Cambiar la fuente es fácil — solo se modifica el Repository, ni la View ni el ViewModel se tocan.
✓
El estado de carga es explícito — la UI puede mostrar indicadores mientras los datos llegan.
✓
Las operaciones lentas no congelan la app — gracias a suspend y viewModelScope.
✓
El código está separado por responsabilidad — cada capa hace lo suyo y nada más.
💡 Ya tienen MVVM completo: capa de UI + capa de datos. Esto es lo que se usa en producción.
