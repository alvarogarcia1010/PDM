El siguiente paso

¿Y por qué quedarnos solo en Android?

Todo lo que aprendieron (separar capas, los repositorios, los ViewModels, no meter lógica en la UI) no tiene por qué vivir solo en Android. ¿Y si les dijera que la misma app, con la misma arquitectura, podría correr también en un iPhone?

💡 Ahí es exactamente donde entra Kotlin Multiplatform.
La idea

¿Qué es Kotlin Multiplatform?

Escribir Kotlin una sola vez y correrlo en varias plataformas: Android, iOS, desktop y web. Lo que compartís es la lógica (datos, red, repositorios, ViewModels), y con Compose Multiplatform hasta la UI.

💡 No es reescribir la app para iOS. Es mover su corazón a un lugar común y dejar afuera solo lo poquito que cada plataforma hace distinto.
Cómo funciona

¿Y cómo corre en un iPhone?

El mismo código Kotlin se compila a la forma nativa de cada plataforma. Para Android se vuelve bytecode de la JVM; para iOS, Kotlin/Native lo compila con LLVM a un binario nativo de verdad — el mismo tipo de binario que produce Swift.

Tu código Kotlin
→
Kotlin/JVMAndroid
→
Kotlin/NativeiOS
💡 No es una capa de traducción ni una máquina virtual encima. Es código nativo en cada lado, así que rinde igual que una app hecha a mano para cada plataforma.
Cómo funciona

Cómo iOS usa tu código Kotlin

El módulo compartido (shared) no se queda en Kotlin. Al compilar, se empaqueta como un framework nativo de Apple — el mismo formato que tiene cualquier librería de iOS.

sharedtu código Kotlin
→
.frameworknativo de Apple
→
Swiftlo importa
💡 Swift importa ese framework como cualquier librería: tus clases Kotlin (repositories, ViewModels) aparecen como clases Swift. No hay un puente raro en medio — es interoperabilidad nativa. Por eso iosApp es tan poquito código.

Por qué les va a costar poco

La buena arquitectura paga acá

Como nunca metieron lógica en la UI ni ataron las capas de datos a Android, casi todo se mueve tal cual a la zona compartida:

  • Los Repository (interfaz e implementación).
  • Los ViewModel con sus StateFlow.

💡 Separar capas no era un capricho académico: es justo lo que hoy les deja saltar de plataforma.
El concepto

Los source sets

Un proyecto KMP organiza el código en carpetas según dónde corre:

commonMainlo compartido
androidMainsolo Android
iosMainsolo iOS
💡 La meta es meter casi todo en commonMain, y dejar en androidMain e iosMain solo lo que cada plataforma hace diferente.
El concepto

expect / actual

Para lo poquito específico de cada plataforma existe expect/actual: en común declarás qué necesitás, y cada plataforma da su cómo.

// commonMain: el contrato
expect fun platformName(): String

// androidMain: el cómo en Android
actual fun platformName() = "Android"

// iosMain: el cómo en iOS
actual fun platformName() = "iOS"

Es como una interfaz, pero a nivel de plataforma.

Un proyecto nuevo

Así nace un proyecto KMP

No hay que armar nada a mano. El Kotlin Multiplatform Wizard (kmp.jetbrains.com) o el plugin de KMP en Android Studio te generan el esqueleto listo.

  • Elegís las plataformas: Android e iOS.
  • Marcás "Share UI with Compose Multiplatform" para compartir también la pantalla.
  • Descargás, abrís en Android Studio, y ya corre.
💡 En un par de minutos tenés un proyecto que ya arranca en Android y en iPhone, sin escribir una línea.
Un proyecto nuevo

Cómo se ve por dentro

shared/            -> el codigo compartido (la libreria KMP)
  commonMain/      -> el corazon: corre en todas partes
  androidMain/     -> lo especifico de Android
  iosMain/         -> lo especifico de iOS

androidApp/        -> la app de Android (punto de entrada)
iosApp/            -> el proyecto de Xcode (punto de entrada de iOS)
💡 commonMain es el corazón: lo que pongas ahí corre en todas partes. iosApp es un pequeño envoltorio de Xcode que hospeda la UI.
Un proyecto nuevo

Correrlo, y el momento mágico

Android corre en cualquier computadora. iOS necesita una Mac con Xcode.

💡 La demo que vale oro: cambiás un texto en commonMain, le das run a Android y a iOS, y el mismo cambio aparece en los dos. Ahí es donde hace clic.

Sin Mac, el target de Desktop sirve igual para la demo: corre en Windows y Linux, y muestra la misma UI compartida.

El plan

Los pasos para convertir

  • 1. Convertir el módulo a multiplatform.
  • 2. Mover la lógica compartida a commonMain.
  • 3. Resolver lo específico con expect/actual.
  • 4. Compartir la UI con Compose Multiplatform.
  • 5. Armar el punto de entrada de iOS.
  • 6. Ajustar las dependencias por plataforma.
Paso 1

El módulo a multiplatform

Se aplica el plugin de KMP y se declaran los targets (Android e iOS), con sus source sets.

kotlin {
    androidTarget()
    iosArm64()
    iosSimulatorArm64()

    sourceSets {
        commonMain.dependencies { /* lo compartido */ }
        androidMain.dependencies { /* solo Android */ }
        iosMain.dependencies { /* solo iOS */ }
    }
}
Paso 2

La lógica a commonMain

Acá está el grueso del trabajo, y es el más fácil: mover archivos. Los models, DTOs, repositories y ViewModels se van a commonMain casi sin tocarlos.

viewmodel

💡 Si algo no compila al moverlo, casi siempre es porque dependía de algo de Android. Eso es justo lo que arregla el paso 3.
Paso 3

Lo específico, con expect/actual

En su app, son contadas las cosas que cada plataforma hace distinto:

  • El motor de Ktor: OkHttp en Android, Darwin en iOS.
  • El builder de Room: cada plataforma da la ruta del archivo.
  • La ruta de DataStore: igual, depende del sistema.
// commonMain
expect val httpEngine: HttpClientEngineFactory<*>
// androidMain
actual val httpEngine = OkHttp
// iosMain
actual val httpEngine = Darwin

El resto del KtorClient (JSON, logging, headers) vive en común sin cambios.

Paso 4

La UI, con Compose Multiplatform

Como toda su UI ya está en Compose, las pantallas se mueven a commonMain. Material 3, LazyColumn, sus Composables: todo funciona igual en iOS.

💡 El mismo MovieListScreen que escribieron para Android se dibuja, sin reescribirlo, en un iPhone. Ese es el momento mágico.

Coil 3 y su AsyncImage también son multiplataforma, así que los afiches cargan igual.

Paso 4 · navegación

Navigation 3, también compartida

Desde Compose Multiplatform 1.10, Navigation 3 corre en todas las plataformas. Su NavDisplay y su back stack se mueven a commonMain tal cual.

💡 El único ajuste: en iOS, las llaves de ruta (NavKey) necesitan serialización polimórfica explícita, porque iOS no tiene la reflexión que usa Android. Es registrar cada ruta una vez. Nada del otro mundo.
Pasos 5 y 6

iOS y las dependencias

Falta el punto de entrada de iOS: una pequeña app en SwiftUI que hospeda la UI de Compose. Es poco código, y casi siempre es el mismo.

Y ajustar las dependencias por source set: el core en común, el motor por plataforma.

commonMain  →  ktor-client-core, room-runtime, datastore, ...
androidMain →  ktor-client-okhttp
iosMain     →  ktor-client-darwin
Lo honesto

Lo que sí cuesta

No todo es gratis, y vale decirlo:

  • Para compilar y correr iOS necesitás una Mac.
  • Lo que toca Context, permisos o recursos de Android hay que abstraerlo.
  • iOS es terreno más nuevo: estable, pero con menos ejemplos y alguna aspereza.
💡 Aun así, el grueso del trabajo es mover código, no reescribirlo. Y eso es gracias a cómo lo armaron.
El premio

La moraleja del ciclo

💡 La buena arquitectura no se nota cuando todo va bien. Se nota el día que tenés que cambiar algo grande, como saltar a otra plataforma.

Separar capas, usar Repository, no meter lógica en la UI, depender de interfaces y no de Android: cada decisión de este ciclo es la que hoy convierte un proyecto entero a iOS moviendo archivos.
