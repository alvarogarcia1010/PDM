1 · ¿Por qué Room?

Hasta ahora, los datos de la app vivían en memoria: mientras la app estaba abierta existían, y al cerrarla se esfumaban. Para una lista de opciones que queremos administrar, eso no sirve. Necesitamos persistencia: guardar información más allá del ciclo de vida de la app.

Android trae SQLite, una base de datos local, desde siempre. Pero usarla a mano es tedioso y propenso a errores: escribís SQL como texto, mapeás cada fila a objeto vos mismo, y los errores recién aparecen cuando la app ya está corriendo. Room es una librería de Jetpack que se pone encima de SQLite y te ahorra todo eso.

¿Por qué Room y no SQLite a mano?

Porque Room verifica tus consultas al compilar (si te equivocás en una query, no compila), mapea las filas a objetos por vos, y se integra con Flow para avisarte en vivo cuando los datos cambian. Menos código, menos errores.

Ese último punto, el Flow, es clave para nuestra meta. Vamos a hacer que la pantalla observe la base de datos: cuando agregués o borrés una opción, la lista se redibuja sola, sin que vos le digas "actualizate". La base de datos manda; la UI solo refleja lo que hay en ella. Eso es Room como fuente de la verdad.

2 · Las 3 piezas

Room se arma con tres componentes. Vale la pena tenerlos claros antes de escribir código:

① Entity

La tabla. Una clase que define qué se guarda y con qué columnas.

② DAO

El menú de operaciones: insertar, consultar, borrar. Una interfaz; Room la implementa.

③ Database

La clase central que junta las entities y da acceso a los DAOs.

Y una pieza de apoyo nueva que vamos a conocer hoy: el AppProvider, que arma todas estas piezas y se las entrega a quien las necesite. Lo vemos en detalle en el Paso 7.

Paso 0La estructura de carpetas

Antes de empezar a programar, conviene tener claro dónde va cada cosa. Todo lo relacionado con datos vive en una carpeta llamada data (es la "capa de datos" del patrón). Y adentro, cada cosa va en su propia carpeta según su responsabilidad: lo local, lo del API y los repositories, separados, y cada carpeta con sus cosas.

app/src/main/java/com/agarcia/rankeuca/data/
data/
├── database/             ← lo LOCAL, con Room
│   ├── dao/
│   │   └── OptionDao.kt
│   ├── entities/
│   │   └── OptionEntity.kt
│   └── AppDatabase.kt
├── remote/               ← lo del API con Ktor (llega más adelante)
├── repository/
│   ├── OptionRepository.kt
│   └── OptionRepositoryImpl.kt
├── model/
│   └── Option.kt
└── AppProvider.kt        ← arma y reparte las dependencias

Qué hace cada carpeta:

database/ guarda todo lo de Room: adentro tiene dao/ (los DAO), entities/ (las entities, o sea las tablas) y la AppDatabase. Esta carpeta no sabe nada del API.

remote/ es para todo lo del API (el cliente Ktor y los DTOs). Hoy queda vacía; se llena cuando consumamos el server. Y al revés que la anterior, no sabe nada de la base de datos.

repository/ tiene los repositories, que son la frontera. El repository es el único que conoce a las dos fuentes (la base local y el API) y las une. La pantalla solo le habla a él.

model/ son los modelos de dominio que usa el resto de la app, como Option. Y AppProvider.kt es el que arma todas las piezas y las reparte (lo vemos en el Paso 7).

La idea de fondo

Cada carpeta tiene una sola responsabilidad: database no sabe del API, remote no sabe de la base, y el repository es el que los junta. Hoy llenamos database/, model/, repository/ y AppProvider; la carpeta remote/ la dejamos lista para cuando entre Ktor.

Paso 1Dependencias (KSP + Room)

Antes de agregar las dependencias, vale la pena entender qué es KSP, porque es la pieza que hace que Room "funcione mágicamente".

KSP (Kotlin Symbol Processing) es una herramienta que deja que ciertas librerías lean tu código anotado al momento de compilar y generen código nuevo a partir de él. ¿Por qué importa? Porque más adelante vos vas a escribir un DAO que es solo una interfaz con anotaciones (@Query, @Insert), sin escribir el SQL ni la implementación. Alguien tiene que leer esas anotaciones y generar la clase real que habla con SQLite. Ese "alguien" es el compilador de Room, y corre justamente a través de KSP.

En otras palabras: KSP es el motor que, en cada build, convierte tus anotaciones de Room en código de verdad. (Reemplaza a kapt, el procesador viejo, y es bastante más rápido porque está hecho a la medida de Kotlin.)

Con eso claro, lo declaramos en el version catalog:

gradle/libs.versions.toml
[versions]
room = "2.8.4"
ksp  = "2.3.9"

[libraries]
room-runtime  = { group = "androidx.room", name = "room-runtime",  version.ref = "room" }
room-ktx      = { group = "androidx.room", name = "room-ktx",      version.ref = "room" }
room-compiler = { group = "androidx.room", name = "room-compiler", version.ref = "room" }

[plugins]
ksp = { id = "com.google.devtools.ksp", version.ref = "ksp" }

Y lo usamos en el build.gradle.kts del módulo (app):

app/build.gradle.kts
plugins {
    // ...tus plugins de siempre
    alias(libs.plugins.ksp)
}

dependencies {
    // ...tus dependencias de siempre
    implementation(libs.room.runtime)
    implementation(libs.room.ktx)
    ksp(libs.room.compiler)
}

Cada dependencia cumple un rol: room-runtime es el motor de Room en ejecución, room-ktx suma el soporte para corrutinas y Flow, y room-compiler es el generador de código. Fijate que este último va con ksp(...) y no con implementation(...): eso es justo lo que le dice a KSP "corré el compilador de Room en cada build".

¿Por qué Room "adivina" la implementación?

No adivina nada: la genera. Cuando compilás, KSP lee tu @Dao y escribe por detrás una clase (algo como OptionDao_Impl) con todo el SQL ya armado. Vos nunca la ves ni la tocás, pero es la que de verdad trabaja. Por eso una simple interfaz "funciona".

Paso 2La Entity: OptionEntity

La entity es la tabla. Cada propiedad es una columna. Para nuestras opciones de RankeUCA, una opción tiene un nombre (el lugar) y una imagen.

data/database/entities/OptionEntity.kt
@Entity(tableName = "options")
data class OptionEntity(
    @PrimaryKey(autoGenerate = true)
    val id: Int = 0,
    val name: String,
    val imageUrl: String,
)

Tres cosas que explicar acá:

@Entity(tableName = "options") le dice a Room "esta clase es una tabla, llamala options". @PrimaryKey(autoGenerate = true) hace que el id sea el identificador único y que Room lo asigne solo, por eso le ponemos val id: Int = 0: cuando creás una opción nueva la dejás en 0, y Room le pone el número real al guardarla.

¿Por qué autoGenerate?

Para no tener que inventar IDs a mano (y arriesgarnos a repetirlos). Vos solo das el nombre y la imagen; del id se encarga la base.

Paso 3El modelo de dominio y el mapper

Acá va una decisión de arquitectura importante, la misma que usamos con Ktor: no usamos la entity directamente en la pantalla. Tenemos un modelo aparte, Option, que es el que ve el resto de la app.

data/model/Option.kt
data class Option(
    val id: Int = 0,
    val name: String,
    val imageUrl: String,
)

Y un par de mappers para convertir entre los dos. toModel() pasa de la entity (de la base) al modelo (de la app), y toEntity() al revés. Es exactamente la misma idea del toModel() que usamos al consumir el API con Ktor.

data/database/entities/OptionEntity.kt
// en el mismo archivo de la entity, debajo de la data class

fun OptionEntity.toModel(): Option {
    return Option(
        id = id,
        name = name,
        imageUrl = imageUrl,
    )
}

fun Option.toEntity(): OptionEntity {
    return OptionEntity(
        id = id,
        name = name,
        imageUrl = imageUrl,
    )
}
¿Por qué separar entity y modelo si son casi iguales?

Porque la entity es un detalle de cómo se guarda (lleva anotaciones de Room), y el modelo es lo que la app usa. Hoy se parecen, pero mañana la entity puede cambiar (una columna nueva, una relación) sin obligarte a tocar toda la app. La frontera te protege.

Paso 4El DAO: OptionDao

El DAO es una interfaz con las operaciones que le vamos a pedir a la base. No la implementás vos: Room escribe la implementación a partir de las anotaciones.

data/database/dao/OptionDao.kt
@Dao
interface OptionDao {

    @Query("SELECT * FROM options")
    fun getAllOptions(): Flow<List<OptionEntity>>

    @Insert(onConflict = OnConflictStrategy.REPLACE)
    suspend fun insertOption(option: OptionEntity)

    @Delete
    suspend fun deleteOption(option: OptionEntity)
}

Fijate en dos detalles que importan:

La consulta devuelve Flow<List<OptionEntity>>, no una lista normal. Un Flow es un stream que emite cada vez que los datos cambian. Por eso la lista de la pantalla se va a actualizar sola cuando agregués o borrés algo: está escuchando este Flow.

Las operaciones que modifican (insert, delete) son suspend, porque tocar la base de datos es trabajo que no debe correr en el hilo principal (si no, trabás la UI). El onConflict = REPLACE dice: si insertás algo con un id que ya existe, reemplazalo.

¿Por qué Flow para leer y suspend para escribir?

Leer es algo continuo: querés enterarte de cada cambio → Flow. Escribir es una acción puntual que tarda un toque → suspend, para hacerla fuera del hilo principal sin congelar la pantalla.

Paso 5La Database (y su singleton)

La clase AppDatabase es la pieza central: declara qué entities tiene y da acceso a los DAOs. Es abstracta: Room la implementa por debajo.

data/database/AppDatabase.kt
@Database(
    entities = [OptionEntity::class],
    version = 1,
    exportSchema = false
)
abstract class AppDatabase : RoomDatabase() {

    abstract fun optionDao(): OptionDao

    companion object {
        @Volatile
        private var INSTANCE: AppDatabase? = null

        fun getDatabase(context: Context): AppDatabase {
            return INSTANCE ?: synchronized(this) {
                Room.databaseBuilder(
                    context = context.applicationContext,
                    klass = AppDatabase::class.java,
                    name = "rankeuca_database"
                )
                    .fallbackToDestructiveMigration(false)
                    .build()
                    .also { INSTANCE = it }
            }
        }
    }
}

El companion object con getDatabase() garantiza que en toda la app exista una sola instancia de la base de datos (un singleton). Abrir la base es caro; no querés hacerlo en cada pantalla.

¿Por qué tanto cuidado con la instancia única?

@Volatile + synchronized evitan que, si dos partes de la app piden la base al mismo tiempo, se creen dos instancias. Te asegura una sola, de forma segura entre hilos. Y fijate que usamos context.applicationContext (nunca el de una Activity) para no fugar memoria.

El detalle de la versión

version = 1 es la versión del esquema. Cuando en el taller agreguemos otra tabla, vamos a subirla a 2. fallbackToDestructiveMigration(false) define cómo reacciona Room a esos cambios. Por ahora no te preocupés: con una sola tabla y versión 1 no hay nada que migrar.

Paso 6El Repository

El Repository es la frontera entre la app y los datos. La pantalla y el ViewModel le piden a él, sin saber si por detrás hay una base local o un API. Lo armamos en dos archivos: primero la interfaz (el contrato, lo que se puede pedir) y luego su implementación (el cómo). Hoy, como es solo local, el cómo queda bien sencillo: traduce lo que da el DAO al modelo de la app.

Primero la interfaz:

data/repository/OptionRepository.kt
interface OptionRepository {
    fun getOptions(): Flow<List<Option>>
    suspend fun addOption(option: Option)
    suspend fun deleteOption(option: Option)
}

Y en un archivo aparte, la implementación, que es la que de verdad habla con el DAO:

data/repository/OptionRepositoryImpl.kt
class OptionRepositoryImpl(
    private val optionDao: OptionDao
) : OptionRepository {

    override fun getOptions(): Flow<List<Option>> {
        return optionDao.getAllOptions().map { entities ->
            entities.map { it.toModel() }
        }
    }

    override suspend fun addOption(option: Option) {
        optionDao.insertOption(option.toEntity())
    }

    override suspend fun deleteOption(option: Option) {
        optionDao.deleteOption(option.toEntity())
    }
}
Acá vive "Room como fuente de la verdad"

Mirá getOptions(): devuelve el Flow del DAO (o sea, lo que hay en Room) mapeado a modelo. La app lee de Room, punto. Cuando más adelante metamos Ktor, el API no le hablará a la pantalla, solo guardará en Room, y como la pantalla escucha este Flow, se enterará sola. Hoy sembramos esa idea con datos puramente locales.

Paso 7El AppProvider y la Application

Ojo: dos cosas nuevas

En este paso aparecen dos conceptos que ves por primera vez: el AppProvider y la clase Application. Léelo con calma, porque son la base de cómo se arma toda la app, y los vas a usar de aquí en adelante en cada proyecto.

Ya tenemos todas las piezas, pero hay un detalle que quizá no saltaba a la vista. Mirá la cadena de dependencias: el ViewModel necesita el Repository, el Repository necesita el DAO, y el DAO sale de la base de datos. Cada cosa necesita la de abajo.

Si dejáramos que cada clase creara lo que necesita por su cuenta, terminaríamos con bases de datos repetidas regadas por toda la app, código acoplado y un desorden difícil de mantener. La solución es tener un solo lugar que cree todo una sola vez y se lo reparta a quien lo pida. A eso se le llama inyección de dependencias, y como lo hacemos a mano (sin librerías), es inyección de dependencias manual.

¿Qué es la inyección de dependencias?

En lugar de que una clase cree las cosas que necesita, alguien externo se las entrega ya listas. Así una clase solo se preocupa por su trabajo, no por construir sus herramientas. El AppProvider es ese "alguien externo": el contenedor que arma las dependencias y las inyecta.

El AppProvider

Entonces, nuestro AppProvider hace justo eso: crea la base (una sola, con el singleton del paso anterior), saca el DAO, arma el repository, y lo expone con un método provide…() para que cualquiera lo pida sin tener que construirlo.

data/AppProvider.kt
class AppProvider(context: Context) {

    private val appDatabase = AppDatabase.getDatabase(context)
    private val optionDao = appDatabase.optionDao()

    private val optionRepository: OptionRepository =
        OptionRepositoryImpl(optionDao)

    fun provideOptionRepository(): OptionRepository {
        return optionRepository
    }
}

Leelo de arriba abajo y vas a ver la cadena armándose: primero la base, de la base sale el optionDao, con el DAO se construye el optionRepository, y provideOptionRepository() es la "ventanilla" por donde lo entregamos. Cuando en el taller agreguemos más cosas, las vas a ir sumando acá mismo.

¿Y la clase Application?

Acá viene la segunda cosa nueva. Android tiene una clase especial llamada Application: es la primera que se crea cuando abrís la app, antes que cualquier pantalla, y vive durante toda la vida de la app (no se destruye al cambiar de pantalla, como sí les pasa a las Activities). Por eso es el lugar perfecto para guardar cosas que toda la app necesita, como nuestro AppProvider.

Creamos nuestra propia clase que hereda de Application y le colgamos el appProvider con by lazy, así se construye recién la primera vez que alguien lo usa:

RankeUcaApplication.kt
class RankeUcaApplication : Application() {
    val appProvider by lazy { AppProvider(this) }
}
El nombre va según tu paquete

No la llames literalmente RankeUcaApplication si tu proyecto se llama distinto. La convención es: el nombre se arma a partir del nombre de tu app / packageName más Application. Si tu paquete es com.tucarnet.rankeuca, queda bien RankeUcaApplication; si fuera com.tucarnet.miapp, sería MiAppApplication. Lo importante es que el nombre refleje tu propia app.

No te olvides del Manifest

Para que Android use tu clase Application, registrala en el AndroidManifest.xml, dentro de la etiqueta <application> (con el mismo nombre que le pusiste a tu clase):

AndroidManifest.xml
<application
    android:name=".RankeUcaApplication"
    ... >

Paso 8El ViewModel

El ViewModel cumple lo mismo de siempre: le da a la pantalla la lista de opciones y las acciones de agregar y borrar. Pero acá hay un cambio de fondo que vale la pena entender bien, porque es distinto a cuando consumías la API.

ui/options/OptionsViewModel.kt
class OptionsViewModel(
    private val optionRepository: OptionRepository
) : ViewModel() {

    val options: StateFlow<List<Option>> =
        optionRepository.getOptions()
            .stateIn(
                scope = viewModelScope,
                started = SharingStarted.WhileSubscribed(5_000),
                initialValue = emptyList()
            )

    fun addOption(name: String, imageUrl: String) {
        viewModelScope.launch {
            optionRepository.addOption(Option(name = name, imageUrl = imageUrl))
        }
    }

    fun deleteOption(option: Option) {
        viewModelScope.launch {
            optionRepository.deleteOption(option)
        }
    }

    companion object {
        val Factory = viewModelFactory {
            initializer {
                val app = this[APPLICATION_KEY] as RankeUcaApplication
                OptionsViewModel(app.appProvider.provideOptionRepository())
            }
        }
    }
}

Pedir una vez vs dejar la comunicación abierta

Acá está el cambio de fondo. Cuando traías datos de la API (el de movies), el repo te daba un Result de una sola vez: pedías con loadMovies(), te respondía, y ahí quedaba hasta que volvieras a pedir (por eso tenías un refreshMovies()).

Con Room es distinto: getOptions() te da un Flow que se queda abierto, emitiendo una lista nueva cada vez que cambia la tabla. Entonces, en vez de pedir y soltar, dejamos una comunicación abierta.

Eso es justo lo que hace stateIn: agarra ese Flow vivo y lo expone como un StateFlow que la pantalla observa. Mientras la pantalla esté mirando, el canal queda activo: agregás una opción, Room emite la lista nueva, y la pantalla se actualiza sola. Nunca tenés que llamar a un refresh a mano.

La comunicación queda abierta

Esta es la diferencia grande con la API: antes pedías una foto del momento; con Room te quedás suscrito a un video en vivo. Por eso un CRUD local con Room se siente casi mágico: tocás la base y la UI reacciona sola, sin recargas.

¿Y el _loading, _error y _refresh del de movies? Hoy no los necesitamos: esos eran por la red (mostrar el spinner, avisar si la conexión falló). Como esto es local y reactivo, no hay espera ni fallo de red que mostrar. Vuelven cuando entre Ktor.

El Factory: de dónde sale el repository

Ese companion object con el Factory también es nuevo para ustedes, y es importante entenderlo. El detalle es este: nuestro OptionsViewModel recibe un repository en el constructor, pero los ViewModel no los creás vos a mano, los crea el sistema de Android por vos. Y el sistema, por defecto, solo sabe crear ViewModels con constructor vacío. Si el tuyo necesita algo (como el repository), tenés que enseñarle cómo construirlo. Para eso sirve el Factory.

Y leelo con cuidado, porque acá se cierra el círculo de la inyección de dependencias:

  • this[APPLICATION_KEY] es la forma de alcanzar tu clase Application desde adentro del factory.
  • De esa Application sacamos su appProvider (el que armamos en el Paso 7).
  • Le pedimos el repository con provideOptionRepository().
  • Y se lo pasamos al OptionsViewModel al construirlo.
Acá se conecta todo

El AppProvider construyó el repository (Paso 7) y el Factory lo inyecta en el ViewModel. Ese es el viaje completo de la inyección de dependencias manual: alguien arma la dependencia en un solo lugar, y otro la entrega donde se necesita. El ViewModel ni se entera de cómo se creó su repository, solo lo recibe listo para usar.

Paso 9La pantalla

Por fin lo visible. La pantalla tiene un Scaffold con su barra superior, un estado vacío cuando todavía no hay opciones, la lista en tarjetas, y un bottom sheet para crear una opción nueva. Ese bottom sheet lo dejamos en su propio archivo (un componente aparte) y solo lo usamos desde la pantalla.

Acá no nos vamos a detener en cada detalle de Compose, eso ya lo manejás. Lo que de verdad importa entender son dos cosas: cómo la pantalla obtiene el ViewModel (el Factory) y cómo observa los datos (collectAsStateWithLifecycle). A esas dos les ponemos lupa más abajo.

Y el bottom sheet, en su propio archivo. Por eso va como fun normal (no private), para poder usarlo desde la pantalla:

ui/options/OptionBottomSheet.kt
@OptIn(ExperimentalMaterial3Api::class)
@Composable
fun OptionBottomSheet(
    onSave: (name: String, imageUrl: String) -> Unit,
    onDismiss: () -> Unit
) {
    val sheetState = rememberModalBottomSheetState()
    var name by rememberSaveable { mutableStateOf("") }
    var imageUrl by rememberSaveable { mutableStateOf("") }

El Factory en acción

Mirá la firma de la pantalla: viewModel(factory = OptionsViewModel.Factory). Acá es donde el Factory que escribiste en el Paso 8 entra en juego de verdad. La función viewModel(...) es la que crea el ViewModel (o te devuelve el que ya existe); al pasarle tu Factory, le decís "no lo armés con constructor vacío, usá mi receta". Y esa receta es la que va al AppProvider a traer el repository. Resultado: la pantalla recibe un ViewModel ya conectado a Room, sin saber nada de bases ni repositories.

collectAsStateWithLifecycle

val options by viewModel.options.collectAsStateWithLifecycle(). Tu options es un StateFlow (lo armaste con stateIn). Este collectAsStateWithLifecycle() lo observa y lo convierte en estado de Compose: cada vez que el StateFlow emite una lista nueva, options cambia y la pantalla se recompone sola. (Viene de androidx.lifecycle:lifecycle-runtime-compose; si no te resuelve, agregá esa dependencia.)

El "WithLifecycle" es lo clave: solo colecta mientras la pantalla está visible, y se pausa cuando se va a segundo plano. Combina perfecto con el WhileSubscribed del stateIn: juntos arman el canal vivo que se prende cuando hay alguien mirando y se apaga cuando no, sin gastar recursos de más.
