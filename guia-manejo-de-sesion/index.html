Login y sesión: la app que te recuerda

El usuario entra una vez, guardamos su sesión con DataStore, y la app lo recuerda hasta que cierre sesión.

En esta guía armamos el login de punta a punta: la pantalla, la llamada a la API, guardar la sesión para no pedir credenciales cada vez, y que la navegación decida sola entre la pantalla de login y el resto de la app.

La pieza nueva de hoy: DataStore

Para recordar al usuario necesitamos guardar algo en el teléfono (el token de sesión). Para eso usamos DataStore, la forma moderna de guardar datos chiquitos y simples en Android.

1El flujo del login

El login no es solo una pantalla bonita. Son cuatro momentos encadenados:

Logincredenciales
→
APIdevuelve token
→
DataStoreguarda
→
Appte recuerda

El usuario mete su correo y contraseña, la API le responde con un token (su llave de sesión), guardamos ese token en DataStore, y de ahí en adelante la app sabe que está logueado. La próxima vez que abra, ni le pedimos login: ya hay token guardado.

Qué es un token

Es un texto que el servidor te da cuando te logueás, y que prueba quién sos. En vez de mandar tu contraseña en cada petición, mandás el token. Si lo borrás (logout), la sesión se cierra.

2El contrato de la API

Antes de tocar Android, hay que saber qué pide y qué devuelve el login. Lo de abajo es un ejemplo de lo que debería devolver el endpoint de login de la API de su proyecto. Tómenlo como referencia y ajústenlo a la suya:

POST /auth/login
// Le mandamos:
{
  "email": "ana@uca.edu.sv",
  "password": "123456"
}

// Si las credenciales están bien (200):
{
  "token": "eyJhbGciOiJIUzI1NiIsInR5cCI6...",
  "user": { "id": 1, "name": "Ana", "email": "ana@uca.edu.sv" }
}

// Si están mal (401):
{ "error": "Credenciales inválidas" }
De aquí salen los DTOs

Ese JSON es justo lo que vamos a modelar con DTOs: uno para lo que mandamos (LoginRequestDto) y otro para lo que recibimos (LoginResponseDto).

3DataStore: guardar la sesión

Para que la app recuerde al usuario hay que guardar el token en el teléfono. La herramienta moderna para eso es DataStore: guarda datos pequeños y simples (pares clave-valor) de forma asíncrona, sin bloquear la app, y te los entrega como un Flow, igual que Room. Acá es donde vamos a guardar el token de sesión y el nombre del usuario.

¿Hay otra forma de guardarlo?

Sí, y vale la pena conocer las dos alternativas:

• Las SharedPreferences de toda la vida hacen lo mismo, pero son la versión vieja. DataStore las reemplaza justamente por ser asíncrono y trabajar con Flow, así que entre las dos elegimos DataStore.

• Para datos de verdad sensibles, lo ideal es guardarlos cifrados (por ejemplo usando el Android Keystore). Un token de sesión idealmente iría cifrado, pero eso es más complejo y queda fuera del scope. Para aprender el patrón, DataStore en texto plano está perfecto; solo tené presente que en una app real lo endurecerías.

Primero la dependencia, en el catálogo de versiones:

gradle/libs.versions.toml
[versions]
datastore = "1.2.1"

[libraries]
androidx-datastore-preferences = { group = "androidx.datastore", name = "datastore-preferences", version.ref = "datastore" }

Creamos el DataStore una sola vez, a nivel de archivo (como una propiedad de extensión sobre Context):

data/session/SessionManager.kt (arriba del archivo)
val Context.dataStore: DataStore<Preferences> by preferencesDataStore(name = "session")

Y armamos un SessionManager que envuelve DataStore: sabe leer el token (como Flow) y guardarlo o borrarlo.

data/session/SessionManager.kt
class SessionManager(private val context: Context) {

    companion object {
        private val TOKEN_KEY = stringPreferencesKey("auth_token")
        private val NAME_KEY = stringPreferencesKey("user_name")
    }

    // Lectura reactiva: emite cada vez que cambia
    val token: Flow<String?> = context.dataStore.data.map { it[TOKEN_KEY] }
    val userName: Flow<String?> = context.dataStore.data.map { it[NAME_KEY] }

    suspend fun save(token: String, name: String) {
        context.dataStore.edit { prefs ->
            prefs[TOKEN_KEY] = token
            prefs[NAME_KEY] = name
        }
    }

    suspend fun clear() {
        context.dataStore.edit { it.clear() }
    }
}
Por qué un Flow otra vez

Que el token sea un Flow es lo que hace toda la magia: cuando guardás o borrás el token, quien lo esté observando se entera al toque. Así la navegación va a saber sola cuándo mostrar el login y cuándo el home.

4Los DTOs del login

Modelamos el contrato de la API. Uno para la petición, uno para la respuesta, y uno para el usuario que viene adentro:

data/api/Auth/AuthDtos.kt
@Serializable
data class LoginRequestDto(
    val email: String,
    val password: String
)

@Serializable
data class LoginResponseDto(
    val token: String,
    val user: UserDto
)

@Serializable
data class UserDto(
    val id: Int,
    val name: String,
    val email: String
)

5El AuthRepository

El repositorio junta las dos mitades: le pega a la API para loguear, y usa el SessionManager para guardar el token. También expone si hay sesión activa, como Flow.

data/repositories/AuthRepository.kt
interface AuthRepository {
    val isLoggedIn: Flow<Boolean>
    val userName: Flow<String?>
    suspend fun login(email: String, password: String)
    suspend fun logout()
}
data/repositories/AuthRepositoryImpl.kt
class AuthRepositoryImpl(
    private val session: SessionManager
) : AuthRepository {

    // Hay sesión si hay token guardado
    override val isLoggedIn: Flow<Boolean> = session.token.map { it != null }
    override val userName: Flow<String?> = session.userName

    override suspend fun login(email: String, password: String) {
        val response: LoginResponseDto = KtorClient.client.post("auth/login") {
            contentType(ContentType.Application.Json)
            setBody(LoginRequestDto(email, password))
        }.body()

        // Login exitoso: guardamos la sesión
        session.save(response.token, response.user.name)
    }

    override suspend fun logout() {
        session.clear()
    }
}
Fijate el orden en login()

Primero le pegamos a la API. Si las credenciales están mal, body() tira excepción y nunca llegamos a guardar nada. Solo si el login sale bien, guardamos el token. Igual que con las mutaciones del offline-first: primero la API, luego lo local.

6El cableado

El AuthRepository necesita un SessionManager, que a su vez necesita el Context. Eso lo arma tu AppProvider, igual que el repositorio de películas.

Conectá el AuthRepository

En tu AppProvider, agregá lo necesario para entregar el AuthRepository ya armado con su SessionManager. Las Factories lo van a pedir así:

  • app.appProvider.provideAuthRepository()

El SessionManager necesita el Context de la aplicación, que ya tenés en el AppProvider.

7El AuthViewModel

El ViewModel expone el estado de sesión y maneja el login con su carga y su error, igual que veníamos haciendo.

AuthViewModel.kt
class AuthViewModel(
    private val repository: AuthRepository
) : ViewModel() {

    // null = todavía no sabemos (DataStore cargando)
    val isLoggedIn: StateFlow<Boolean?> = repository.isLoggedIn
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), null)

    val userName: StateFlow<String?> = repository.userName
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), null)

    private val _isLoading = MutableStateFlow(false)
    val isLoading: StateFlow<Boolean> = _isLoading.asStateFlow()

    private val _error = MutableStateFlow<String?>(null)
    val error: StateFlow<String?> = _error.asStateFlow()

    fun login(email: String, password: String) {
        viewModelScope.launch {
            _error.value = null
            _isLoading.value = true
            try {
                repository.login(email, password)
            } catch (e: Exception) {
                _error.value = "Correo o contraseña incorrectos"
            }
            _isLoading.value = false
        }
    }

    fun logout() {
        viewModelScope.launch { repository.logout() }
    }
}
El estado arranca en null, no en false

Cuando la app abre, DataStore tarda un instante en cargar. Si arrancáramos en false, se vería un parpadeo del login antes de saltar al home. Por eso isLoggedIn empieza en null: significa "todavía no sé", y mostramos una pantalla de carga mientras tanto.

8La pantalla de login

Un formulario simple: correo, contraseña, un botón que se desactiva mientras carga, y el error si las credenciales fallan.

screens/Login/LoginScreen.kt
@Composable
fun LoginScreen(
    viewModel: AuthViewModel = viewModel(factory = AuthViewModel.Factory)
) {
    var email by rememberSaveable { mutableStateOf("") }
    var password by rememberSaveable { mutableStateOf("") }

    val isLoading by viewModel.isLoading.collectAsState()
    val error by viewModel.error.collectAsState()

    Column(
        modifier = Modifier.fillMaxSize().padding(24.dp),
        verticalArrangement = Arrangement.Center
    ) {
        Text("Bienvenido a RankeUCA", style = MaterialTheme.typography.headlineSmall)
        Spacer(Modifier.height(24.dp))

        OutlinedTextField(
            value = email,
            onValueChange = { email = it },
            label = { Text("Correo") },
            singleLine = true,
            modifier = Modifier.fillMaxWidth()
        )
        Spacer(Modifier.height(12.dp))

        OutlinedTextField(
            value = password,
            onValueChange = { password = it },
            label = { Text("Contraseña") },
            singleLine = true,
            visualTransformation = PasswordVisualTransformation(),
            modifier = Modifier.fillMaxWidth()
        )

        if (error != null) {
            Spacer(Modifier.height(8.dp))
            Text(error!!, color = MaterialTheme.colorScheme.error)
        }

        Spacer(Modifier.height(20.dp))
        Button(
            onClick = { viewModel.login(email, password) },
            enabled = !isLoading && email.isNotBlank() && password.isNotBlank(),
            modifier = Modifier.fillMaxWidth()
        ) {
            if (isLoading) CircularProgressIndicator(modifier = Modifier.size(20.dp))
            else Text("Entrar")
        }
    }
}
Detalles que cuidamos

El botón se desactiva si los campos están vacíos o mientras carga, así no se manda un login a medias. Y la contraseña va con PasswordVisualTransformation() para que se vea con puntitos.

9La navegación según la sesión

Acá está el premio de todo lo anterior. La frontera entre estar logueado y no estarlo la decide el estado de sesión, no la navegación normal. Por eso la ponemos arriba de todo, antes del back stack.

El AppRoot mira isLoggedIn y elige: pantalla de carga, login, o la app completa. Y la app completa ya usa Navigation 3, igual que en la app de películas. Primero, las llaves de las rutas:

navigation/Routes.kt
@Serializable data object MovieList : NavKey
@Serializable data class MovieDetail(val id: Int) : NavKey

Luego el AppRoot, que decide según la sesión:

AppRoot.kt
@Composable
fun AppRoot(
    authViewModel: AuthViewModel = viewModel(factory = AuthViewModel.Factory)
) {
    val isLoggedIn by authViewModel.isLoggedIn.collectAsState()

    when (isLoggedIn) {
        null -> SplashScreen()          // DataStore todavía cargando
        false -> LoginScreen()          // sin sesión
        true -> MainNavigation(         // con sesión: la app completa
            userName = authViewModel.userName.collectAsState().value,
            onLogout = { authViewModel.logout() }
        )
    }
}

Y la parte logueada usa Navigation 3 como siempre: un back stack propio y un NavDisplay con las pantallas.

navigation/MainNavigation.kt
@Composable
fun MainNavigation(userName: String?, onLogout: () -> Unit) {
    val backStack = rememberNavBackStack(MovieList)

    NavDisplay(
        backStack = backStack,
        onBack = { backStack.removeLastOrNull() },
        entryProvider = entryProvider {
            entry<MovieList> {
                MovieListScreen(
                    userName = userName,
                    onLogout = onLogout,
                    navigateToDetail = { id -> backStack.add(MovieDetail(id)) }
                )
            }
            entry<MovieDetail> { key ->
                MovieDetailScreenV2(
                    movieId = key.id,
                    navigateBack = { backStack.removeLastOrNull() }
                )
            }
        }
    )
}
El login vive afuera del back stack

Fijate que el login no es una pantalla más del NavDisplay. La frontera con sesión / sin sesión la decide el estado, no el back stack.

Así, cuando alguien cierra sesión, no "navegás" al login: el estado cambia, el when reacciona, y todo el back stack de la app se descarta entero. Sin el típico bug de apretar atrás y volver a una pantalla privada.

10Cerrar sesión

El logout es lo más simple de todo, justamente porque la navegación es reactiva. Borrás el token, y la app vuelve sola al login.

en el Home, un botón
Button(onClick = onLogout) {
    Text("Cerrar sesión")
}
// onLogout llama a viewModel.logout(), que borra el token del DataStore.
// isLoggedIn pasa a false, y AppRoot muestra el LoginScreen otra vez.

11Mandar el token (para cuando protejas la API)

Hoy nuestra API está abierta, así que el token no hace falta para nada después de loguearte. Pero el día que protejás algún endpoint, vas a tener que mandar el token en cada petición. Así se hace:

data/api/KtorClient.kt
object KtorClient {

    // Se actualiza al loguear y al cerrar sesión
    var authToken: String? = null

    val client = HttpClient(OkHttp) {
        defaultRequest {
            url(BASE_URL)
            authToken?.let { header(HttpHeaders.Authorization, "Bearer $it") }
        }
        // ... resto de la config ...
    }
}
Cómo se mantiene actualizado

Al loguear, ponés KtorClient.authToken = token. Al cerrar sesión, lo dejás en null. Y al abrir la app, lo cargás desde DataStore. Para apps más grandes, Ktor tiene el plugin Auth que automatiza esto, pero para empezar, esta versión se entiende mejor.

12Checkpoint

Tu login está completo cuando:

Deberías tener funcionando

• La pantalla de login manda las credenciales y muestra error si están mal.
• Tras loguearte, la app salta sola al home y te saluda con tu nombre.
• Si cerrás la app y la volvés a abrir, seguís logueado (no te pide login de nuevo).
• El botón de cerrar sesión te regresa al login, también solo.

13Tu turno

Integrá este login en tu app de RankeUCA, contra el endpoint de login que vas a tener disponible.

Lo que tenés que entregar
  • Una pantalla de login que valide contra la API y guarde la sesión en DataStore.
  • Que la app recuerde la sesión: si la cerrás y la abrís, seguís adentro.
  • La navegación reactiva: sin sesión se ve el login, con sesión se ve la app.
  • Un saludo al usuario con su nombre, y un botón de cerrar sesión.
Acordate de la pantalla de carga

El detalle de arrancar isLoggedIn en null y mostrar un splash mientras DataStore carga es lo que evita el parpadeo del login al abrir. No te lo saltés: es lo que separa una app que se siente pulida de una que titila.

Puntos de aceptación

Tu entrega está lista cuando:

• Con credenciales correctas, entrás y la app te recuerda al reabrir.
• Con credenciales incorrectas, ves un mensaje claro y no entrás.
• El logout te saca y te devuelve al login, sin navegar a mano.
• No hay parpadeo del login al abrir la app con sesión activa.
